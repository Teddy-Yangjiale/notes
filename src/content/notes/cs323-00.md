## 2. 为什么要学编译器

- **深入理解程序**：高层抽象 → 机器操作的完整转换链路；代码与硬件的关系。
- **程序分析与代码优化**：写高性能代码、做系统工作的基本功。
- **语言设计与实现**：DSL（领域特定语言）应用极广。
- **现代工具的底层技术**：例如深度学习编译器（Apache TVM）把 DL 框架模型作为输入，为目标硬件（专用加速器）生成优化后的可执行代码。

> 一句话：编译器是形式语言理论 + 算法 + 数据结构 + 体系结构 + 软件工程的交汇点，是"计算思维"的终极训练。

## 3. 编程语言的演化

### 3.1 语言的分层

- **低级语言（low-level）**：机器可直接理解（0/1 序列）。
- **高级语言（high-level）**：人可读，需要**翻译器**才能被机器理解。
- 现存编程语言 700+ 种。

### 3.2 三个阶段

| 阶段 | 时间 | 特征 |
|---|---|---|
| 机器语言 | 1946，ENIAC | 靠拨开关、接电缆编程，纯 0/1 |
| 汇编语言 | 1950s 初 | 用**助记符**（mnemonic）代替机器指令，**宏指令**代替常用指令序列；仍需显式操作内存地址，仍然低级且机器相关 |
| 高级语言 | 1950s 后半 | Fortran（科学计算）、Cobol（商业数据处理）、Lisp（符号计算） |

**补充**：ENIAC 常被称为第一台电子计算机，但更早的 ABC（Atanasoff–Berry Computer）才是第一台自动电子数字计算机——它不可编程、非图灵完备，只能解线性方程组。

### 3.3 汇编语言的缺点（催生高级语言）

- 编程冗长且慢；
- 程序人类难以阅读；
- 易错、难调试。

### 3.4 Fortran：第一个高级语言

- 1953 年 John Backus 提议为 IBM 704 开发比汇编更实用的替代方案。
- **1957 年**交付第一个 Fortran（Formula Translation）编译器。
- 1958 年 50%+ 的软件用 Fortran 写成。
- 影响深远：**现代编译器仍保留 Fortran I 的结构轮廓**。
- Backus 因此获 1997 年图灵奖；Fortran 至今仍在 TIOBE 榜前列（2026 年 8 月第 15）。

## 4. 编译器的经典结构 ★（本讲核心）

```
             ┌──────────────────────────┐
 Source  →   │ Lexical Analyzer  词法分析 │ ┐
 Code        │ Syntax Analyzer   语法分析 │ ├ Frontend 前端（分析部分）
             │ Semantic Analyzer 语义分析 │ │
             │ Intermediate Code Gen     │ ┘
             ├──────────────────────────┤  → IR + 符号表
             │ Machine-Independent       │ ┐
             │   Code Optimizer          │ │
             │ Code Generator            │ ├ Backend 后端（综合部分）
             │ Machine-Dependent         │ │
             │   Code Optimizer          │ ┘
             └──────────────────────────┘  → Machine Code
```

### 4.1 前端（Frontend，分析部分）

- 把源程序**拆成构成部件**，并施加**语法结构**；
- 用语法结构创建源程序的**中间表示（IR）**；
- 收集源程序信息存入**符号表（symbol table）**，与 IR 一起传给后端。

### 4.2 后端（Backend，综合部分）

- 由 IR + 符号表**构造目标程序**（通常是机器语言）；
- 过程中执行各类代码优化。

> 历史变化：早期词法/语法分析最复杂最昂贵；**今天优化阶段占主导**，lexing 和 parsing 已经很便宜。

## 5. 七个阶段逐个拆解

### 5.1 词法分析（Lexical Analysis / Scanning）

```
Character stream → [Lexical Analyzer] → Token stream
```

- 词法分析器（lexer / tokenizer / scanner）把源码切成**词素（lexeme）**；
- 每个词素产生一个**词法单元（token）**，形式为：

  `<token-name, attribute-value>`

  - `token-name`：语法分析阶段使用的抽象符号；
  - `attribute-value`：指向符号表中的一个条目，其中的信息供语义分析与代码生成使用。

**Lexeme vs Token（易混，必考概念）**

| | Lexeme 词素 | Token 词法单元 |
|---|---|---|
| 是什么 | 程序语言中最低层的语法单位，一串具体字符 | 表示一类词素的**语法范畴** |
| 类比英语 | "SUSTech"、"is" 这些具体词 | Noun、Verb、Adjective 这些词类 |
| 层次 | 实例（instance） | 模式（pattern） |

**例子**：`position = initial + rate * 60`

| 输出 token | 符号表 |
|---|---|
| `<id, 1>` | 1 → position |
| `<=>` | 2 → initial |
| `<id, 2>` | 3 → rate |
| `<+>` | |
| `<id, 3>` | |
| `<*>` | |
| `<60>` | |

> 注：`<=>` `<+>` `<*>` `<60>` 写成这样只是记号上的方便，规范写法应是 `<assign, ->`、`<number, 4>` 之类。

英语类比：`SUSTech is a great university` → `<noun,"SUSTech"> <verb,"is"> <article,"a"> <adjective,"great"> <noun,"university">`

### 5.2 语法分析（Syntax Analysis / Parsing）

```
Token stream → [Syntax Analyzer] → Syntax tree
```

- 用词法单元名构造出反映**文法结构**的中间表示，通常是**语法树（syntax tree）**；
- 每个内部结点表示一个**运算**，其子结点表示该运算的**参数**。

例子的语法树：

```
        =
      /   \
  <id,1>   +
         /   \
     <id,2>   *
            /   \
        <id,3>   60
```

英语类比：句子 → 主语 / 谓语 / 宾语 的层次结构。

### 5.3 语义分析（Semantic Analysis）

```
Syntax tree → [Semantic Analyzer] → Syntax tree (带类型等信息)
```

- 使用语法树与符号表信息，检查源程序与语言定义的**语义一致性**；
- 收集**类型信息**，供类型检查、类型转换和中间代码生成使用。

**语法 vs 语义**

- **语法（syntax）**：描述程序的正确**形式**；
- **语义（semantics）**：描述程序的**含义**，即执行时做什么。

**语义的歧义难题（英语类比）**

- *Jack said Jerry left his assignment at home.* — "his" 指谁？
- *Jack said Jack left his assignment at home.* — 有几个 Jack？

编程语言用**严格规则**消除歧义。例如：

```c
{
  int Jack = 3;
  {
    int Jack = 4;
    print Jack;   // 绑定到内层第 4 行的定义 → 打印 4
  }
}
```

**类型检查（Type Checking）**是语义分析的重要部分：检查每个运算符的运算分量类型匹配。

```java
double x = 3.2;
int[] nums = new int[5];
nums[x] = 6;   // 错误：数组下标必须是整数，编译器应报错
```

> 理解程序的"含义"极其困难，所以编译器只做**非常有限**的分析（如类型检查）来捕捉语义不一致。

### 5.4 中间代码生成（Intermediate Code Generation）

```
Syntax tree → [Intermediate Code Generator] → IR（通常为三地址码）
```

**三地址码（three-address code）**的特点：

- 类汇编指令，每条指令最多 3 个运算分量；
- 每个运算分量像一个寄存器；
- 每条赋值指令右侧最多一个运算符；
- 易于翻译成目标机器指令。

例：

```
t1 = inttofloat(60)
t2 = id3 * t1
t3 = id2 + t2
id1 = t3
```

### 5.5 机器无关的代码优化（Machine-Independent Optimization）

```
IR → [Machine-Independent Code Optimizer] → IR
```

目标：让目标代码**跑得更快 / 占内存更少 / 代码更短 / 更省电**。类比英语文章的润色。

对上例的优化推理：

1. `60` 是整型常量，它到浮点的转换可以在**编译期**一次性完成（常量折叠）；
2. `t2`、`t3` 只用于传值（可消除）。

优化后：

```
t1 = id3 * 60.0
id1 = id2 + t1
```

### 5.6 代码生成（Code Generation）

```
IR → [Code Generator] → Target-machine code
```

- 把 IR 映射到目标语言；
- **关键在于寄存器与内存的分配**。

```asm
LDF  R2, id3
MULF R2, R2, #60.0
LDF  R1, id2
ADDF R1, R1, R2
STF  id1, R1
```

### 5.7 符号表管理（Symbol Table Management）

由前端完成，随中间代码一起传给后端。记录：

- **变量名**及其属性：分配的存储、类型、作用域；
- **过程名**及其属性：参数个数与类型、传参方式（传值/传引用）、返回类型。

## 6. 中间语言（IL）为什么重要

中间代码写在某种中间语言里（如三地址码）。好的 IL 能极大简化编译器实现：

| | 没有好的 IL | 有好的 IL |
|---|---|---|
| M 种语言 × N 种目标机 | 需要 **M × N** 个编译器 | 需要 **M + N** 个（M 个前端 + N 个后端） |

这正是 LLVM IR、TVM 等现代基础设施成立的根本原因。
