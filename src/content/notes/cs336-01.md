## 1. 本讲要解决什么问题

这一讲有两条主线：先解释为什么要从零构建语言模型，再以 tokenizer 为第一个完整组件，展示“定义目标—分析约束—实现算法—验证结果”的课程方法。

学习后应能回答：

1. 一个现代语言模型系统由哪些阶段组成，每个阶段的核心约束是什么？
2. 为什么模型能力不能只由“架构是否新颖”解释？
3. tokenizer 为什么必要，字符、字节、词级方案分别失败在哪里？
4. Byte Pair Encoding（BPE）如何训练、编码和解码？
5. 如何判断 tokenizer 正确且实用，而不只是在样例上能运行？

## 2. 课程方法论：理解来自亲手构建

### 2.1 抽象层正在升高，但底层问题没有消失

语言模型研究的工作方式经历了明显变化：早期研究者自己实现并训练模型，之后更多是下载预训练模型微调，现在大量工作直接调用闭源 API。抽象层提高能提升生产力，但语言模型的抽象仍然“会漏”：tokenizer、数据分布、数值精度、并行布局、推理批处理等底层选择都会改变上层行为。

因此课程的目标不是复刻一个前沿模型，而是让学生打通完整链路：

```text
原始数据
  → 清洗、过滤、去重、混合
  → tokenizer 训练与编码
  → Transformer 前向与损失
  → 反向传播、优化器、训练循环
  → kernel 与分布式扩展
  → 推理服务与评测
  → SFT / 偏好优化 / RLVR
```

只会其中一个 API 并不能解释系统为什么有效，也无法在规模、数据或硬件变化时定位问题。

### 2.2 `accuracy = efficiency × resources`

课件用一个工程化等式概括模型进步：

```text
最终能力 ≈ 算法与系统效率 × 可用资源
```

它不是严格数学公式，而是研究判断框架：

- **效率**包括样本效率、参数效率、优化稳定性、硬件利用率和推理效率。
- **资源**包括训练数据、加速器数量、显存、网络带宽、工程时间和实验预算。
- 相同 FLOPs 下，更好的数据、架构或优化器能降低 loss；相同算法下，更多可靠算力通常仍会带来收益。

“Bitter Lesson”的含义不是算法设计无用，而是可扩展、能持续吃到更多计算和数据的方法，长期往往压过依赖人工规则的方案。研究新方法时必须问：收益能否在更大模型、更长训练和真实系统中保持？

### 2.3 小模型实验能告诉我们什么

前沿模型昂贵且细节不公开，课程只能训练较小模型。小模型仍可用于验证：

- 实现是否正确；
- 优化方向是否具有局部收益；
- 资源账本和复杂度分析是否吻合；
- 某种训练不稳定是否已经出现。

但不能自动外推：不同规模下 attention/MLP 的 FLOPs 比例会变化，涌现行为可能只在特定尺度出现，小模型上的最优超参数也未必可迁移。因此后续需要 scaling laws 来管理外推风险。

## 3. 语言模型的完整技术栈

### 3.1 建模基础

- **Tokenization**：把原始 Unicode 字符串变为有限词表中的整数序列。
- **Architecture**：embedding、位置编码、attention、MLP、残差与归一化。
- **Training**：通常以 next-token prediction 训练自回归模型。

对 token 序列 $x_1,\ldots,x_T$，自回归分解为：

$$
p(x_{1:T})=\prod_{t=1}^{T}p(x_t\mid x_{<t}),
$$

训练使用负对数似然：

$$
\mathcal L=-\frac{1}{T}\sum_{t=1}^{T}\log p_\theta(x_t\mid x_{<t}).
$$

tokenizer 会直接改变 $T$、词表大小和“一个 token 代表什么”，所以它不是无关紧要的预处理。

### 3.2 系统

- **Kernel**决定单个算子如何映射到 GPU；
- **Parallelism**决定参数、激活和样本如何分布到设备；
- **Inference**分为可并行处理 prompt 的 prefill，以及逐 token、常受内存带宽限制的 decode。

常用训练 FLOPs 粗略估计为：

$$
C\approx 6ND,
$$

其中 $N$ 是非 embedding 参数量，$D$ 是训练 token 数。系数 6 来自每 token 约 $2N$ 的前向矩阵乘与约两倍前向的反向计算。它适合数量级估算，不替代 profiler。

### 3.3 Scaling、数据、评测与对齐

- scaling laws 决定固定预算下模型大小 $N$ 与数据量 $D$ 如何分配；
- 数据工作包括来源、版权、抽取、质量过滤、去重和混合；
- 评测必须明确被测对象、提示格式、污染风险和统计不确定性；
- 后训练把“预测互联网文本”的模型变成遵循指令、满足偏好并能完成可验证任务的助手。

## 4. Tokenization 的形式化目标

Tokenizer 是一对函数：

$$
\operatorname{encode}: \text{string}\rightarrow [0,V)^*,\qquad
\operatorname{decode}: [0,V)^*\rightarrow \text{string}.
$$

最基本的正确性条件是往返一致：

$$
\operatorname{decode}(\operatorname{encode}(s))=s.
$$

实用 tokenizer 还要同时满足：

1. **有限且可控的词表**：embedding 和输出层成本通常与 $V$ 成正比。
2. **覆盖任意输入**：不能因为遇到罕见字符或新词就丢信息。
3. **压缩率合理**：序列越短，attention 和训练成本通常越低。
4. **统计效率**：常见模式应共享参数，罕见模式不应独占大量 token。
5. **可逆和确定**：相同输入、相同 tokenizer 参数必须得到相同结果。

课程用 bytes per token 衡量压缩率：

$$
r=\frac{|s.\operatorname{encode}(\text{UTF-8})|}{|\operatorname{encode}(s)|}.
$$

$r$ 越高表示每个 token 覆盖的原始字节越多，但高压缩率并不自动意味着更好的模型：词表过大会增加参数和稀疏性，跨语言压缩不均还会造成计算配额不公平。

## 5. 三种直接方案为什么不够

### 5.1 字符级 tokenizer

算法是对每个 Unicode code point 使用 `ord`，解码用 `chr`。优点是概念简单、序列比纯字节略短；问题是：

- Unicode code point 空间很大；
- 大量字符极少出现，却需要独立 embedding；
- 字符集合难以用固定小词表完整覆盖；
- 组合字符、规范化形式和 emoji 会让“一个人眼字符”不等于一个 code point。

### 5.2 字节级 tokenizer

先把字符串编码为 UTF-8，再把每个字节 $0\ldots255$ 当作 token。它只有 256 个基础 token，对任何可编码文本都无 OOV，且天然可逆。

缺点是序列很长。例如一个汉字通常占 3 个 UTF-8 字节；模型必须在多层网络中反复学习稳定的字节组合。字节级方案覆盖性最好，但在当前 Transformer 上计算效率较差。

### 5.3 词级 tokenizer

按空格或规则切词能获得较高压缩率，但存在：

- 词表规模不受控；
- 低频词的 embedding 学不到可靠统计；
- 新词需要 `<UNK>`，信息不可逆；
- 对中文、代码、黏着语和标点规则并不统一；
- 训练和测试分词规则稍有变化就会造成分布漂移。

BPE 的目标正是取得折中：以字节保证覆盖，以数据驱动的合并缩短常见模式。

## 6. BPE 训练算法

### 6.1 状态表示

训练需要维护两个核心对象：

- `vocab[token_id] -> bytes`：每个 token 实际代表的字节串；
- `merges[(left_id, right_id)] -> new_id`：按训练顺序记录合并规则。

初始化时：

$$
V_0=\{0,1,\ldots,255\},
$$

且 `vocab[i] = bytes([i])`。把训练文本 UTF-8 编码后得到初始整数序列 $z^{(0)}$。

### 6.2 单轮合并

第 $k$ 轮执行：

1. 统计当前序列中所有相邻二元组 $(z_i,z_{i+1})$ 的频次；
2. 选择频次最大的 pair $(a,b)$；
3. 分配新编号 $u=256+k$；
4. 保存 `merges[(a,b)] = u`；
5. 保存 `vocab[u] = vocab[a] + vocab[b]`；
6. 从左到右把所有不重叠的 $(a,b)$ 替换为 $u$。

伪代码：

```python
ids = list(text.encode("utf-8"))
vocab = {i: bytes([i]) for i in range(256)}
merges = {}

for k in range(num_merges):
    counts = count_adjacent_pairs(ids)
    if not counts:
        break
    pair = deterministic_argmax(counts)
    new_id = 256 + k
    merges[pair] = new_id
    vocab[new_id] = vocab[pair[0]] + vocab[pair[1]]
    ids = merge_left_to_right(ids, pair, new_id)
```

### 6.3 为什么替换必须“不重叠”

若序列是 `[a,a,a]`，目标 pair 是 `(a,a)`，一次扫描不能同时合并位置 `(0,1)` 与 `(1,2)`，因为它们共享中间 token。正确实现通常是：匹配成功后输出 `new_id` 并前进两位，否则复制当前 token 并前进一位。

### 6.4 合并顺序就是模型参数

相同最终词表不代表相同 tokenizer。后续 token 可能由早期 token 组成，因此编码必须尊重 merge rank。训练中的并列频次也要制定确定性 tie-break，例如按字节串字典序，否则不同运行可能生成不同词表。

### 6.5 复杂度

最朴素实现每轮都重新扫描长度 $n_k$ 的序列：

$$
T=\sum_{k=1}^{M}O(n_k)\le O(Mn_0),
$$

其中 $M$ 是 merge 数。真实大语料训练通常需要：

- 预分词并统计“片段频数”，避免存储完整展开序列；
- 增量更新受合并影响的相邻 pair 计数；
- 用堆或桶维护高频 pair，同时处理过期计数；
- 将 special token 从普通合并中隔离；
- 并行统计后做确定性归并。

## 7. 使用训练好的 BPE

### 7.1 编码

课程中的教学实现按 `merges` 插入顺序依次应用规则：

```python
ids = list(text.encode("utf-8"))
for pair, new_id in merges.items():
    ids = merge_left_to_right(ids, pair, new_id)
return ids
```

更高效的编码器会反复从当前相邻 pair 中选择 rank 最小、即训练时最早学到的可用规则，并用链表/优先队列降低重复扫描成本。无论实现方式如何，输出必须与 merge rank 语义一致。

### 7.2 解码

解码不需要逆序拆 merge，只需：

```python
raw = b"".join(vocab[token_id] for token_id in ids)
text = raw.decode("utf-8")
```

单个 token 的字节串不一定独立构成合法 UTF-8；只有拼接后的整体才应解码。因此调试 tokenizer 时不要假设每个 token 都能单独显示为字符。

### 7.3 Special tokens

`<|endoftext|>`、BOS、EOS 等 special token 具有协议语义，不应让普通 BPE 偶然合并得到。工程实现通常先在原始文本中识别 special token，把普通片段分别编码，再插入预留 ID。还必须显式规定允许哪些 special token，避免用户文本被意外解释为控制符。

## 8. Tokenizer 对模型训练的实际影响

### 8.1 序列长度和计算

若同一文本从 $T$ 个 token 压缩到 $T/c$，全注意力的 $O(T^2)$ 项理论上缩小约 $c^2$，MLP 等按 token 线性计算的部分缩小约 $c$。但更大的词表会增加：

$$
P_{embed}\approx Vd,
$$

并使输出 softmax 更昂贵，所以不能无限追求合并。

### 8.2 语言与数字偏差

- 空格是否与后续词合并，会让句首和句中同一词使用不同 token；
- 数字按几位分组会影响算术泛化；
- 不同语言的 bytes/token 差异会使相同语义消耗不同上下文和推理费用；
- 代码中的缩进、标点和长标识符会产生不同于自然语言的最优切分。

因此 tokenizer 是数据分布和系统成本的一部分，而不是纯粹的字符串工具。

## 9. 实现与验收清单

### 正确性

1. 多语言、emoji、空串、控制字符满足 round-trip；
2. 每个输出 ID 都在词表范围；
3. merge 不重叠且顺序确定；
4. 保存后重新加载得到完全相同的编码；
5. special token 与普通文本边界正确。

### 性能与质量

1. 在独立验证语料上统计 bytes/token，而非只测训练文本；
2. 分语言、代码、数字分别报告压缩率；
3. 统计 token 频率长尾，排查大量几乎从未出现的 token；
4. 测训练吞吐和 encode 吞吐；
5. 比较不同词表大小对序列长度、embedding 参数和下游 loss 的联合影响。

## 10. 常见误区

- **“Unicode 字符就是人眼字符”**：组合字符和 emoji 序列会反例。
- **“字节 token 会 OOV”**：完整 256 字节词表能覆盖任意字节串；OOV 是词级方案的典型问题。
- **“BPE 是按词做合并”**：本讲实现从 UTF-8 字节开始；实际系统可先做 regex 预分词，但基本合并对象仍由具体 tokenizer 定义。
- **“最终 vocab 相同就等价”**：merge rank 不同会产生不同编码。
- **“压缩率越高越好”**：还要考虑词表参数、统计稀疏性、跨语言公平和模型 loss。
- **“小模型结果可以直接外推前沿规模”**：必须结合 scaling 实验和系统瓶颈重新验证。

## 11. 本讲知识链

```text
原始 Unicode
  → UTF-8 bytes（保证覆盖）
  → 统计相邻 pair
  → 逐轮学习 merge 与 vocab（适应数据分布）
  → 按 merge rank 编码
  → token 序列进入自回归 Transformer
  → token 数影响训练 FLOPs、上下文容量和推理成本
```

本讲最重要的思想是：语言模型的每个“接口层”都同时是统计决策和系统决策。BPE 看似只是预处理，却共同决定了模型看到的数据单位、可学习的规律和实际计算成本。
