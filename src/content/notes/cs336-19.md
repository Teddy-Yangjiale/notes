## 1. 主线：Inference 是把电力变成 token 的引擎（00:00–00:06）

讲座把大模型创新分成相互反馈的三层：

```text
服务层：请求、缓存、调度、SLO
执行层：inference engine、kernel、GPU/专用硬件
模型层：attention、MoE、recurrent/loop architecture
```

只优化一个 operator 往往把瓶颈推到其他层。理解 inference engine 和 GPU kernel 还能反向启发模型架构：如果一种结构能更好复用权重、缓存或片上状态，它可能以相同部署资源提供更高能力。

## 2. 一个 Token 的完整生命周期（00:06–00:17）

请求进入系统后：

1. API gateway/负载均衡接收 prompt 与服务参数；
2. tokenizer 转为 token IDs；
3. scheduler 选择 model replica/worker；
4. 查询 prefix/KV cache，确定已计算前缀；
5. 对新 prompt tokens 执行 prefill；
6. 进入 decode loop；
7. logits processing、sampling/argmax；
8. 检查 EOS、stop strings、长度；
9. 流式返回 token，并更新/保存 KV；
10. 请求结束，释放或保留 cache。

系统必须适配不同 workload：短聊天、数万 token context、长 reasoning、agent 多轮循环、离线 batch。优化平均请求可能伤害 p99 或另一类请求，因此服务策略应以实际 input/output length 和 arrival distribution 为依据。

## 3. Prefill 与 Decode（00:13–00:21）

### Prefill

一次处理 $T_p$ prompt tokens，类似训练 forward：大 GEMM、FlashAttention、较高并行度，往往 compute-heavy。完成后每层写 K/V cache。

### Decode

每步只处理新 token，但必须运行整个模型，并读取权重和历史 KV：

```text
latest token
→ all layers
→ logits
→ sample one token
→ append KV
→ repeat
```

它常 memory-bandwidth-heavy。Speculative decoding 可让一步验证多个候选，但基本依赖仍是自回归。

### Disaggregated Prefill/Decode

把两类负载分到不同 GPU/芯片池：

- prefill pool 为大矩阵/长序列优化；
- decode pool 为低延迟、权重/KV 带宽优化；
- 两者之间传输 KV cache 和请求状态。

好处是独立扩缩容和硬件异构；代价是 KV 网络传输、路由、故障恢复和更复杂的容量规划。只有当阶段差异收益超过转移成本时才有价值。

## 4. 长时间运行的推理正确性（00:21–00:25）

演讲强调 inference kernel bug 可能很隐蔽：短 benchmark 正常，运行数万 tokens 后重复同一 token、进入循环或数值漂移。

验收需要：

- kernel 与 reference 的短序列逐步 logits 对齐；
- 长 decode 的 error accumulation；
- 多 batch、context、dtype 和非整除 shape；
- stop/EOS 与 sampling state；
- NaN/Inf、重复率和异常 entropy 监控；
- cache evict/restore 后结果与未迁移路径一致。

“单次 kernel 输出接近”不证明整条自回归链稳定，因为误差会改变采样 token，之后轨迹完全分叉。

## 5. KV Cache 成为一级系统对象（00:25–00:34）

Prefix KV 命中可跳过重复 prefill。Cache 层级可能是：

```text
GPU HBM：最快、最贵、容量小
→ CPU/Grace memory：更大，传输延迟更高
→ local/remote storage：更大更慢
```

### 5.1 Cache Placement

调度器不应只问“哪张 GPU 空闲”，还要问：

- 该请求的 prefix KV 在哪里？
- 迁移 cache 的 bytes 和时间是多少？
- 重算 prefill 是否更便宜？
- 预计还会 decode 多少 tokens？
- 该 worker 的队列和 SLO 如何？

粗略决策：

$$
T_{route}=T_{queue,hot}+T_{cache/load}
$$

与

$$
T_{cold}=T_{queue,cold}+T_{prefill,recompute}
$$

取满足 SLO 且成本较低者。

### 5.2 Cache-aware Prefill–Decode Scheduling

同一 agent/user 的长前缀可能反复复用。若总把请求发到最空 worker，会丢掉 locality；若只追逐热 cache，又可能形成热点和排队。调度需要在 locality、负载与优先级间权衡，并预测输入/输出长度。

### 5.3 Agentic Workload

agent 循环多次调用模型，每轮共享长 system/repo context，只新增少量 tool result。此时保持 KV “热”特别重要；一次性离线 batch 的前缀复用价值则可能较低（问答约 01:07–01:09）。

## 6. 传统 Multi-kernel Decode 的空洞（00:34–00:37）

普通 engine 为每个 operator 启动 kernel：

```text
norm → QKV GEMM → RoPE → attention → O projection
→ residual/norm → MLP → ...
```

即使单 kernel 已优化，时间线仍有：

- host/kernel launch 与 teardown；
- 前一 kernel tail 只占少数 SM，后一 kernel 尚未开始；
- operator 边界强制中间状态写回/同步；
- decode batch 小，单 kernel 并行工作不足。

这些 gaps 在训练/大 prefill 中可能被大 GEMM 淹没，在低 batch decode 中占比显著。

## 7. Megakernel（00:37–00:42）

Megakernel 把一串 operators 放进一个长寿命 GPU kernel，内部自行调度细粒度 tasks。它比普通 pointwise fusion 更激进：不仅消除中间写回，还跨 attention 各阶段重叠原本有依赖间隙的工作。

### 7.1 跨操作流水

演讲例子：

- QKV+RoPE 尚未完全结束时，提前从 HBM 读取历史 KV；
- attention 某些 tiles 仍在运行时，预取 O-projection weights；
- 不同 SM/warps 执行不同子任务，用 device-side queue/barrier 管理依赖；
- 让 memory loads、matrix work 和 reductions 尽可能并行。

概念时间线：

```text
QKV compute:      [==========]
KV prefetch:          [==========]
attention tiles:          [==============]
O-weight prefetch:              [=======]
O projection:                         [==========]
```

传统 kernels 会把这些框强制串行；megakernel 允许合法部分重叠。

### 7.2 GPU 内部像分布式系统

需要处理：任务队列、生产者/消费者、SM 负载均衡、同步、片上内存复用和 tail。工作粒度过小，调度 overhead 高；过大又回到 tail/不均衡。

### 7.3 ThunderKittens

讲座使用 ThunderKittens 这类比 Triton 更低层的 kernel framework，便于控制 tiles、shared memory 和 sub-kernel scheduling。代价是工程、调试和硬件相关性更高。

### 7.4 报告收益与边界

演讲报告特定 attention decode 场景约 30%–70% 加速、H100 约 72% 带宽利用率。需要与相同 batch/context/dtype/model baseline 比较。问答指出开发极其昂贵：一名优秀 kernel 工程师可能只能为一种硬件、少数模型和 batch 1–16 做好；batch 17 都可能需要重调（约 01:03–01:04）。

因此 Megakernel 适合稳定、量大、形状可控的服务热点，不适合作为所有动态模型的通用替代。

## 8. Parcae：用 Recurrence 扩展计算（00:42–00:45）

Loop Transformer 复用同一组 blocks $R$ 多次：

```text
input layers
→ recurrent block R
→ R
→ ... K recurrences
→ output layers
```

优点：

- 参数量保持，FLOPs 可由 recurrence count $K$ 调节；
- 同权重被多次使用，提高“能力/参数”潜力；
- 参数受限或推理权重带宽受限时更有吸引力；
- 理论上共享参数的迭代计算可表达固定深度、同参数量模型难表达的函数。

但计算不会消失：loop $K$ 次仍支付 $K$ 次 activation compute，且训练深度和反向路径加长。

## 9. 为什么朴素循环不稳定（00:45–00:51）

实验中朴素 recurrent-depth 模型对 LR 很敏感，常有 loss spikes/NaN。以前可在每步强加 norm 或只用某个幸运 LR，但没有解决动力学根因。

演讲把复杂 attention/GELU/MLP 统称非线性块 $R$，分析 residual 的主导线性部分。可抽象为：

$$
h_{t+1}=Ah_t+Bu+R(h_t,u),
$$

$u$ 是进入 loop 的初始输入，$A$ 控制每轮 residual 传播，$B$ 控制初始注入。忽略/线性化 $R$ 后：

$$
h_t=A^th_0+\sum_{i=0}^{t-1}A^iBu.
$$

长期行为由 $A^t$ 主导。若谱半径：

$$
\rho(A)=\max_j|\lambda_j(A)|>1,
$$

某方向会指数放大；即使只略大于 1，循环 16/32 次也可能爆炸。$\rho(A)=1$ 是 marginal stability，非线性和训练更新仍可能推入不稳区域。

## 10. Parcae 的稳定参数化（00:51–00:53）

Parcae 不让 $A,B$ 无约束学习。演讲描述：

- 将 $A$ 约束为稳定的负对角/等价离散谱半径小于 1 的形式，使反复作用衰减而非爆炸；
- 对只应用一次的 $B$ 使用简单线性归一/约束；
- 直接从参数化保证动力系统稳定，而不是让 activation 先膨胀、再用 norm 硬压回。

后者会产生两股相反压力：网络学习放大表示，norm 每轮重新缩小，外观看 activation norm 正常，loss 仍可能 spike。稳定参数化限制根因后，可在原本发散的较高 LR 下获得平滑曲线。

## 11. Parcae 的质量与 Scaling 观点（00:53–01:00）

演讲比较 Parcae、Recurrent Depth Model 和强 Transformer baseline，报告更低 perplexity/更好任务表现。更重要的研究问题是 recurrence 也应纳入 scaling：

$$
L=L(N,D,K),qquad
C\approx \text{FLOPs}(N,D,K).
$$

当数据 $D$ 增长，固定参数可能更值得增加 recurrence $K$，让同一参数接受更多计算；当模型大小受内存约束时，也可用更多循环换能力。训练 compute-optimal 场景仍需在扩大参数与增加 recurrence 间拟合 IsoFLOPs，而不是假设 loop 永远更优。

## 12. Megakernel 与 Loop Model 的协同（问答 01:01–01:06）

Loop model 的同一权重被连续复用，可能：

- 权重更容易留在 cache/片上层级；
- 更小参数 footprint 留出更多 HBM 给 KV cache；
- recurrent block 形状固定，适合专门 Megakernel；
- 在一个 persistent kernel 内直接循环，减少每轮 launch。

但这是潜力而非已普适验证的结论。循环越多，单 token latency 越高；若服务 compute-bound，参数减少未必抵消额外 FLOPs。模型、kernel 和服务 workload 必须共同 co-design。

## 13. 全栈设计的成本模型

对请求可粗略写：

$$
T_{request}=T_{queue}+T_{cache lookup/load}
+T_{prefill}+\sum_{t=1}^{T_o}T_{decode,t}.
$$

总成本还包括：

$$
C_{service}=C_{compute}+C_{HBM}+C_{network}
+C_{cache storage}+C_{engineering/reliability}.
$$

Megakernel 主要降低 $T_{decode}$，cache-aware scheduling 降 $T_{prefill}$/queue，Parcae 改变参数 footprint 与每 token FLOPs。它们作用在不同项，只有端到端测量才能知道瓶颈是否真正下降。

## 14. 验收框架

### 服务层

- TTFT、TPOT、E2E、p95/p99；
- prefix hit rate、cache bytes moved/recomputed；
- workload 分层：chat、long context、reasoning、agent、batch。

### Kernel 层

- 与 reference logits/long decode 对齐；
- HBM bandwidth、SM utilization、launch gaps、tail；
- batch 1–N、不同 context 和非整除 shape；
- H100/Blackwell 等硬件分别调优，不混合结论。

### 模型层

- 固定 parameters、FLOPs、tokens 的公平 baseline；
- recurrence $K$ sweep 和 stability/LR sweep；
- perplexity、下游、latency、KV capacity；
- 训练与部署总成本，而不只 intelligence/parameter。

## 15. 常见误区

- Prefill 与 decode 是不同硬件负载，不能只报统一 tokens/s。
- 最大化 cache 容量不等于最优；慢层级 restore 可能不如重算。
- 单 kernel 很快不代表 multi-kernel decode 没有 launch/tail gaps。
- Megakernel 不只是普通 operator fusion，而是 GPU 内 device-side 调度与跨阶段重叠。
- 演讲性能数字高度依赖 shape、batch、模型和硬件。
- 每轮加 norm 可能遮住 activation 爆炸，但不保证 recurrent dynamics 稳定。
- 谱半径约束解决线性主导稳定性，仍需验证非线性完整模型。
- Loop model 减参数但增 FLOPs；“更高能力/参数”不等于更低延迟。

本讲的核心结论是：推理优化最大的空间常在层与层的接口。调度器要理解 KV locality，kernel 要跨越 operator 边界隐藏数据移动，模型架构也可以用稳定 recurrence 改变参数与计算的比例；全栈协同必须由端到端 SLO、正确性和总成本共同验证。
