## 1. Evaluation 是测量设计

“模型好”是抽象 construct，可能包含知识、推理、帮助性、安全、速度、成本等。评估要把 construct 操作化为：

```text
被测对象
 + 数据/环境
 + 提示与工具协议
 + 解码参数
 + 评分器
 + 聚合与不确定性
= 可复现 measurement
```

同一 base model 配不同 system prompt、tool scaffold、retrieval、sampling 和预算会得到不同结果。报告前必须声明是在评：

- model weights；
- 某个产品/API；
- model + prompt；
- model + agent scaffold + tools；
- 某种训练方法在固定预算下的产物。

## 2. Perplexity（PPL）

对 token 序列 $x_{1:T}$：

$$
\operatorname{NLL}=-\frac1T\sum_{t=1}^T\log p(x_t\mid x_{<t}),
$$

$$
\operatorname{PPL}=e^{\operatorname{NLL}}.
$$

直觉上，PPL 是模型每步“有效候选分支数”的几何平均。若真实分布为 $t$、模型为 $p$：

$$
\mathbb E_t[-\log p]=H(t)+\operatorname{KL}(t\|p),
$$

所以在同一 tokenization/数据分布上，最优 PPL 在 $p=t$ 时达到数据熵对应值。

### 2.1 优点

- 连续、低方差，适合 scaling law 和训练监控；
- 不需要生成长回答或外部 judge；
- 能发现数据/优化器的小幅改进。

### 2.2 限制

- 不同 tokenizer 的 per-token PPL 不可直接比较；可用 bits/byte 等统一单位；
- 对每个 token 等权，可能惩罚不影响任务价值的词；
- test distribution 与真实使用不一致；
- 低 PPL 不保证指令遵循、安全或工具使用；
- API 若只返回截断/不归一 logprobs，PPL 可能无效。

对 prompt–response 任务可只计算 response 条件 NLL：

$$
-\frac1{|y|}\log p(y\mid x),
$$

避免 prompt token 主导分数。

## 3. 选择题与考试 Benchmark

### 3.1 标准评分

若候选答案文本长度不同，比较总 log probability 会偏好短答案；可比较选项标签概率，或长度归一：

$$
s(y)=\frac1{|y|}\sum_t\log p(y_t\mid x,y_{<t}).
$$

必须固定 prompt template、few-shot examples、答案抽取规则和是否允许 CoT。

### 3.2 MMLU、MMLU-Pro、GPQA、HLE

- **MMLU**：多学科考试，主要测知识与基础推断，已接近饱和且存在噪声；
- **MMLU-Pro**：清理简单/含糊题，选项增多，更依赖推理且对 prompt 较稳定；
- **GPQA**：专家撰写的研究生级生物/物理/化学问题，非专家即使可搜索也难，适合研究高难监督；
- **Humanity's Last Exam**：多学科、多模态、选择+短答，继续提高难度。

趋势是 benchmark 被模型追平后不断加难。但考试有明显 construct gap：封闭、单轮、有标准答案，不等于真实开放任务。

### 3.3 统计不确定性

对 $n$ 道独立二元题，accuracy $\hat p$ 的标准误近似：

$$
SE=\sqrt{\frac{\hat p(1-\hat p)}{n}}.
$$

小数据集上 1–2 分差可能不显著。更稳妥做 bootstrap 置信区间和 paired comparison，因为模型在同一题上的结果相关。

## 4. 开放式 Chat 评估

### 4.1 Pairwise Preference

给同一 prompt 的回答 A/B，让人或 LLM judge 选择。由 pairwise wins 可拟合 Bradley–Terry/Elo 风格能力：

$$
P(A\succ B)=\sigma(r_A-r_B).
$$

Chatbot Arena 使用真实用户 prompt 和盲测人类偏好，生态真实性较强；但用户分布不受控、偏好可能受长度、语气、品牌和错误难以核验影响。

### 4.2 LLM-as-a-Judge

优点是便宜、可扩展；风险包括：

- 偏好更长、更多标题或与自己风格相似的回答；
- position bias；
- 无法可靠核验专业事实；
- judge 与被测模型同源导致 self-preference；
- 提示注入攻击评分器。

改进：交换 A/B 顺序、明确 rubric/checklist、要求逐项证据、使用多个 judges、对人类标注校准。AlpacaEval 2.0 用统计回归校正长度偏差；WildBench 从真实对话抽样并用 checklist judge。

Judge 指标本身也必须评估：与高质量人类 pairwise label 的 agreement、系统级 rank correlation、偏差分层和置信区间。

## 5. Agentic Benchmarks

Agent = LM + scaffold + memory + tools + environment policy。评估 agent 时模型不是唯一变量。

### 5.1 SWE-bench

输入真实 GitHub issue 和 repository snapshot，agent 修改代码，最终用 tests 判定。优点是结果可执行验证；难点：

- tests 可能不充分或错误；
- 环境构建失败；
- issue 可能需要隐藏上下文；
- scaffold、工具、token/时间预算显著影响；
- patch 能通过测试但语义不正确。

SWE-bench Verified 通过人工核验提高任务可解性和 test 质量。

### 5.2 Terminal-Bench / CyBench

终端任务可用可执行状态验证，并用人类 first-solve time 估计难度；网络安全任务还具有 dual-use 风险。必须隔离环境、限制网络和记录完整 trace。

### 5.3 评估预算

Agent 可通过更多 rollouts、长上下文、搜索和子代理提高成绩。公平比较需要固定：模型调用次数、tokens、wall-clock、工具权限、并发、重试和人工干预。否则是在比较“总系统投入”，不只是模型能力。

## 6. Pure Reasoning 与 ARC-AGI

ARC 试图用人类容易、AI 困难的新颖网格任务减少知识记忆影响；后续版本增加多步与交互环境。它强调抽象规则归纳，但仍是特定任务分布，且限制在人类可解推理，不覆盖超人知识检索或现实工具工作。

所谓“纯推理”也依赖视觉编码、搜索预算、交互接口和训练污染。任何 benchmark 都不能完全隔离一个抽象心理能力。

## 7. Safety Evaluation

安全不是单一 refusal rate。至少区分：

- 明确有害请求的拒绝/安全完成；
- benign 请求误拒绝；
- jailbreak 鲁棒性；
- 生物、网络、欺诈等领域能力与实际 uplift；
- 隐私、偏见、政治和地区法律；
- agent 获得工具后的行动风险。

HarmBench、AIR-Bench 等提供标准化场景；GCG 等自动攻击通过优化输入后缀寻找越狱。只测固定手写攻击会高估鲁棒性。

Safety–helpfulness 存在 trade-off：模型可通过“全部拒绝”提高某些安全指标，因此必须同时报告 harmful success 和 benign refusal。双用途能力还需比较人类在有/无模型帮助下的增量，而非只看模型能否回答。

## 8. Difficulty、Realism、Validity 三个轴

### 8.1 Difficulty

过易 benchmark 饱和，无法区分前沿模型；过难且几乎全错，也没有分辨率。应覆盖多个难度并报告分层结果。难度可用专家成功率、人类时间或旧模型通过率估计。

### 8.2 Ecological Validity / Realism

评测是否像真实使用：真实 prompt、上下文、工具、长任务、用户分布和后果。考试可控但不真实，Arena 真实但不可控。医疗等领域更需从标准考试转向临床工作流和真实决策支持（如 MedHELM）。

真实性与隐私冲突：真实日志含敏感信息。需要去标识、合成/授权数据、访问控制和报告采样偏差。

### 8.3 Construct Validity

分数变化真的是目标能力变化，还是 prompt、格式解析、污染、test bugs、judge 偏差或 scaffold 差异？有效性必须通过人工审计、基线、ablation 和 error taxonomy 建立。

## 9. Train–Test Overlap 与污染

### 9.1 污染类型

- exact benchmark question/answer 出现在训练集；
- paraphrase、翻译、解答网页或讨论串；
- benchmark 生成模板泄漏；
- 后训练数据专门针对公开测试；
- model/judge 曾接触同一答案。

### 9.2 检测方法

若可访问训练数据：

- exact hash；
- n-gram/MinHash/embedding near-duplicate；
- 搜索 question、answer 和独特短语；
- 按时间 cut-off 构建新测试。

若只有模型：可比较已发布/未发布题的 loss、顺序交换、completion 异常、要求复述来源等，但这些是间接证据，不能可靠证明污染。最有力做法仍是提供方披露 overlap audit。

### 9.3 动态与私有测试

持续新建题、platinum 人工验证、隐藏 tests 能降低污染，但会降低可复现性并增加维护成本。需要版本化 dataset、时间戳和受控 evaluation server。

## 10. Dataset 与 Evaluator 质量

常见缺陷：

- 多个正确答案却只接受一个字符串；
- 问题信息不足；
- tests 太弱，trivial solution 通过；
- environment 不可构建；
- 评分脚本抽取失败；
- task 与声称能力不一致。

改进流程：

1. domain experts 双重审核；
2. human baseline 与 trivial baseline；
3. 查看模型完整输出/agent traces；
4. 按错误类型抽样复核；
5. 修正后发布新版本而非静默改分；
6. 用 Docent 类 trace inspection 辅助发现 benchmark flaws，但仍需人工确认。

## 11. 两种不同的评估目标

### 产品选择

目标是某个使用场景的质量/成本/SLO。应使用真实 workload、业务 rubric、延迟和失败成本；可以比较完整产品系统。

### 研究方法比较

目标是隔离算法贡献。必须固定数据、compute、参数、scaffold、评测协议。例如 nanoGPT speedrun 固定数据和硬件时间，看达到目标 validation loss 的速度。此时开放式产品排名不是合适证据。

## 12. 推荐 Eval Card

每次评估记录：

```text
Question: 想回答什么决策问题？
Object: model / API / agent / method
Dataset: version、来源、采样、时间范围
Protocol: prompt、few-shot、tools、budget、sampling
Metric: 定义、聚合、置信区间
Validity: contamination、judge、dataset audit
Efficiency: cost、latency、tokens、hardware
Limitations: 未覆盖的人群、任务和已知偏差
```

## 13. 常见误区

- PPL 不能跨 tokenizer 直接比较。
- benchmark 高分不自动表示真实用户价值。
- LLM judge 便宜不等于客观；rubric 和偏差校准是必要步骤。
- Agent benchmark 同时测模型、scaffold、工具和预算。
- “未在公开网页搜到”不能证明训练无污染。
- 一两个百分点差异需要统计不确定性和 paired analysis。
- 安全分数必须与 benign refusal、真实 uplift 和上下文一起看。
- 没有唯一真实 evaluation；只有对某个决策问题更合适的测量。

本讲的核心结论是：评估不是训练后的最后一张排行榜，而是模型开发的测量系统。只有明确被测对象，并同时管理难度、现实性和有效性，分数才可能支持可靠决策。
