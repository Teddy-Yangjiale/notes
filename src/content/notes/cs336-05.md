## 1. 为什么大模型依赖 GPU（p.5–19）

Dennard scaling 结束后，单核频率不再持续快速提升；模型计算增长主要依赖并行硬件。CPU 优化少量线程的低延迟和复杂控制流，GPU 优化大量同构工作的总吞吐。

### 1.1 计算层级

```text
GPU
 ├─ 多个 SM（Streaming Multiprocessor）
 │   ├─ 标量/向量 ALU
 │   ├─ Tensor Cores
 │   ├─ registers
 │   ├─ shared memory / L1
 │   └─ warp schedulers
 ├─ 共享 L2
 └─ HBM/global memory
```

- **Thread**：执行一份 kernel 程序的逻辑实例；
- **Warp**：通常 32 个相邻线程，以 SIMT 方式共同发射指令；
- **Block/CTA**：一组线程，被调度到同一个 SM，可共享 shared memory 并同步；
- **Grid**：一次 kernel launch 的全部 blocks。

block 之间不能依赖普通 block-level barrier，跨 block 数据通常经 global memory 或新一轮 kernel 协调。

### 1.2 内存层级

越靠近计算单元，容量越小、带宽越高、延迟越低：

```text
register → shared/L1 → L2 → HBM → host/network
```

Tensor Core 的矩阵吞吐增长快于 HBM 带宽，形成 memory wall。高性能 kernel 的核心不是减少一切运算，而是用较少 HBM 访问喂饱越来越快的计算单元。

### 1.3 Tensor Core

Tensor Core 对固定 tile 的低/混合精度矩阵乘加提供专用电路，峰值通常远高于普通 FP32 标量运算。要用上它，需要 dtype、矩阵布局、维度对齐和 kernel 实现都符合要求；“代码里有 matmul”不保证达到 tensor-core 峰值。

## 2. Roofline 是性能分析起点（p.20–22）

$$
I=\frac{\text{FLOPs}}{\text{HBM bytes}},\qquad
P\le\min(P_{peak},I\cdot BW).
$$

- 算术强度低：HBM-bound；
- 算术强度高：compute-bound；
- 实际远低于二者：还可能是 launch latency、occupancy、依赖链、同步、分支或不规则访问。

优化前要先确定限制项，否则“少算一些”可能反而更慢。

## 3. Warp Divergence（p.23）

同一 warp 的线程遇到不同分支时，硬件通常按 mask 分别执行各路径：

```text
if 分支线程执行 A，其余线程闲置
再让 else 分支线程执行 B，前一组闲置
```

若路径代价相近，最坏接近串行执行两条路径。优化方法：

- 让同一 warp 处理控制流相近的数据；
- 用 predication/无分支算术替代很短分支；
- 把不同类型工作分到不同 kernel；
- 不要为消除分支引入更多昂贵计算或内存访问，必须实测。

## 4. 低精度（p.24–29）

降低位宽同时减少 HBM bytes、cache 占用，并可能启用更快 Tensor Core。对 ReLU，FP32 每元素至少读写约 8 bytes，FP16 约 4 bytes，因此 FLOP/byte 翻倍。

极低精度还需要 scale。MXFP8/FP4 常按 block 共享 scale：

$$
x\approx s_b\,q,
$$

$q$ 是低位值，$s_b$ 是第 $b$ 个 block 的尺度。block 越小，适应局部分布越好但 scale 元数据和量化开销越大。转置不再只是改变 stride：转置后 block 分组方向变化，可能必须保存独立量化版本或重新量化（p.27–29）。

训练中不能只检查平均误差，还要监控饱和率、underflow、amax、scale 延迟、累加精度和梯度稳定性。

## 5. Operator Fusion（p.30–33）

若依次计算五个 pointwise 操作，每一步都启动 kernel、读输入、写中间结果。融合后：

```text
一次读 HBM
→ 寄存器中完成多步计算
→ 一次写 HBM
```

收益来自：

- 减少中间 tensor HBM 往返；
- 减少 kernel launch；
- 可能共享归约/索引计算。

PyTorch 编译器能自动融合许多 pointwise 链，但跨复杂归约、动态 shape 或自定义算子不一定成功。融合也受 register pressure 限制：kernel 过大可能减少每 SM 可并发 blocks，降低 occupancy。

## 6. Recomputation（p.34–36）

反向所需中间值若写回 HBM，再读出，可能比重新计算更贵。例如多层 sigmoid 的中间激活都是低 arithmetic intensity 数据。若重算只需少量标量运算，可以：

```text
forward：不保存部分中间值
backward：从边界输入重算
```

重算用 FLOPs 换 bytes。最优策略取决于算子成本、激活大小和硬件 roofline；不是“所有激活都丢掉”。FlashAttention backward 就会重算局部 attention 概率，以避免保存 $T^2$ 矩阵。

## 7. Coalescing（p.37–39）

DRAM 以对齐 transaction/burst 搬运一段连续字节。若 warp 中相邻线程访问相邻且对齐地址，硬件可合并成少量 transaction；若访问跨很多 cache line/segment，就会发出更多请求，带宽利用率下降。

对 row-major 矩阵，最后一维连续。通常让线程 ID 沿最后一维变化更容易 coalesced。常见陷阱：

- 访问转置矩阵造成大 stride；
- 起始地址未对齐；
- 每行长度使下一行 tile 错位；
- gather/scatter 地址不规则。

必要时通过 padding、改变 layout、向量化 load 或 shared-memory transpose 修复。

## 8. Tiling（p.40–48）

矩阵乘 $C=AB$ 的朴素实现反复从 HBM 读取同一行/列。Tiling 把 $A$、$B$ 子块搬进 shared memory/register：

```text
for K tile:
    cooperative load A_tile, B_tile
    synchronize
    在片上存储中累积 C_tile
写回 C_tile
```

若 tile 宽度为 $T_k$，输入的 HBM 重复读取可粗略减少约 $T_k$ 倍。实际 kernel 还有 block tile、warp tile、MMA tile 多层分块和双缓冲。

### 8.1 Tile 选择约束

- shared memory 容量；
- register 数，过多会 spill 或降低 occupancy；
- warp 数与 SM 并发；
- matrix dimensions 是否整除；
- global load 是否对齐/coalesced；
- Tensor Core 支持的 MMA shape。

### 8.2 Tile quantization 与 Wave quantization

维度从 1792 增到 1793 看似只增加一个元素，但 tile 数会从整除的 $7\times14=98$ 跳到 $8\times15=120$。边缘 tiles 大部分无效；若 GPU 有 108 SM，第二 wave 只有 12 个 tiles，利用率很低。这解释了 GEMM 延迟随 shape 出现锯齿和周期，而不是平滑增长（p.45–48）。

## 9. FlashAttention 的问题定义（p.50–54）

标准 scaled dot-product attention：

$$
S=QK^T/\sqrt d,
\qquad P=\operatorname{softmax}(S),
\qquad O=PV.
$$

朴素实现把 $S,P\in\mathbb R^{T\times T}$ 写到 HBM。计算量仍是 $O(T^2d)$，但巨大的中间矩阵读写使它 IO-bound，并占用 $O(T^2)$ 激活内存。

FlashAttention 不近似结果，也不降低渐近 FLOPs；它通过 IO-aware tiling 避免把完整 $S/P$ materialize 到 HBM。

## 10. Online Softmax 推导

对一行 logits $x_1,\ldots,x_n$，稳定 softmax 需要：

$$
m=\max_i x_i,qquad
l=\sum_i e^{x_i-m}.
$$

若已处理旧块，状态为 $(m_{old},l_{old})$；新块最大值 $m_b$、局部和 $l_b$。合并：

$$
m_{new}=\max(m_{old},m_b),
$$

$$
l_{new}=e^{m_{old}-m_{new}}l_{old}
+e^{m_b-m_{new}}l_b.
$$

旧的输出累积也要按 $e^{m_{old}-m_{new}}$ 重缩放。若同时维护未归一化加权和：

$$
o=\sum_i e^{x_i-m}v_i,
$$

新块可用同样规则更新，最后输出 $o/l$。这使 softmax 可以按 K/V tile 流式计算且与整行结果等价。

## 11. FlashAttention Forward

对每个 Q block：

1. 将 $Q_i$ tile 载入 SRAM；初始化每行 $m=-\infty,l=0,O=0$；
2. 依次载入 $K_j,V_j$ tiles；
3. 在片上计算 $S_{ij}=Q_iK_j^T/\sqrt d$；
4. 应用 causal mask；
5. 用 online softmax 更新 $m,l$ 和 $O$；
6. 所有 K/V blocks 处理完后，把归一化输出写回 HBM。

完整 $T\times T$ logits/概率从未写到 HBM。内存从 $O(T^2)$ 中间存储降为近似 $O(Td)$，HBM IO 大幅减少。

## 12. Backward 的重算思想

forward 保存输出和每行 softmax 统计（如 log-sum-exp），不保存 $P$。backward 按 tile 重新计算：

$$
P_{ij}=\exp(S_{ij}-m_i)/l_i,
$$

再计算 $dV,dP,dS,dQ,dK$。虽然多做一些 $QK^T$ 和指数运算，却避免保存/读取巨大 $P$，在 memory wall 下更快。

## 13. 性能诊断顺序

1. 确认输出和容差正确；
2. 用 shape/dtype 推导 FLOPs 和 bytes；
3. roofline 判断理论瓶颈；
4. profiler 检查 Tensor Core、HBM 带宽、occupancy、launch gaps；
5. 检查 layout、对齐、tile 边界、分支和 fusion；
6. 用多个代表性 shapes 报告 median，而不是只选漂亮尺寸。

## 14. 常见误区

- GPU 的优势是吞吐，不是每个线程都比 CPU 快。
- 高 occupancy 不是最终目标；register 增加可能降低 occupancy，却提高数据复用。
- 低精度同时改变带宽、Tensor Core 路径和数值误差，不能只按 bit 数预测速度。
- fusion 过度会增加 register pressure。
- coalescing 关注一个 warp 发出的地址，不只是 tensor 是否“看起来连续”。
- 大矩阵并非单调更慢，tile/wave 对齐会造成性能断点。
- FlashAttention 是精确 attention 的 IO 优化，不是 sparse/linear attention。

本讲的核心是：GPU 优化的基本货币是数据移动。低精度、融合、重算、合并访问和 tiling 看似不同，实际上都在提高每次昂贵 HBM 搬运产生的有效工作量。
