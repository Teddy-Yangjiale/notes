## 1. 分布式执行的基本对象

- **process/rank**：一个参与者，编号 $0\ldots P-1$；
- **world size**：参与进程总数 $P$；
- **process group**：collective 的参与集合；
- **backend**：GPU 通常用 NCCL，CPU 可用 Gloo；
- **local rank/device**：当前进程在节点内绑定的 GPU。

典型初始化：每个进程设置当前 CUDA device，使用统一 `MASTER_ADDR/PORT` 建立 process group；结束时销毁。所有 ranks 必须以相同顺序进入 collective，否则可能永久等待。

## 2. 点对点与 Collective

### 2.1 Broadcast

root 的 tensor 复制到所有 ranks。常用于初始化参数、配置或随机状态。

### 2.2 Reduce

把所有 rank 的 tensor 按 sum/max 等运算合并到 root：

$$
y=\bigoplus_{r=0}^{P-1}x_r.
$$

### 2.3 All-Reduce

每个 rank 都得到 reduce 结果。数据并行同步梯度最典型：

$$
g=\frac1P\sum_rg_r.
$$

### 2.4 All-Gather

每个 rank 持有不同 shard $x_r$，最终所有 ranks 得到拼接后的完整 $[x_0;\ldots;x_{P-1}]$。

### 2.5 Reduce-Scatter

先逐元素 reduce，再把结果切成 $P$ 个 shards，第 $r$ 个 rank 只得到第 $r$ 片。它不是简单 scatter，因为发送前发生归约。

### 2.6 All-to-All

每个 rank 给每个其他 rank 发送不同 shard。MoE expert routing 与某些 sequence/context parallel 大量依赖它，对网络拓扑和负载均衡更敏感。

## 3. All-Reduce = Reduce-Scatter + All-Gather

在带宽主导下，ring all-reduce 可分两阶段：

1. **reduce-scatter**：tensor 切成 $P$ 块，经过 $P-1$ 轮环传，每轮接收一块并累加；
2. **all-gather**：再经过 $P-1$ 轮环传，让每个 rank 收齐所有已归约块。

每个 rank 的总发送/接收数据近似：

$$
2\frac{P-1}{P}M,
$$

$M$ 是 tensor bytes。这接近带宽下界，解释了 ZeRO 为什么可以把一个 all-reduce拆成 reduce-scatter + all-gather 而不增加带宽量级。

通信时间常用 $\alpha$-$\beta$ 模型：

$$
T\approx n_{messages}\alpha+n_{bytes}\beta,
$$

$\alpha$ 是启动/延迟，$\beta$ 是每 byte 时间。小 tensor 受延迟主导，大 tensor 受带宽主导；只报告 GB/s 会忽略小消息问题。

## 4. 硬件拓扑与 NCCL

节点内可能有 NVLink/NVSwitch，节点间通常是 InfiniBand/RoCE。可用带宽和延迟存在层级：

```text
同 GPU
 < 同 NVLink 域
 < 同节点 PCIe
 < 同机架网络
 < 跨机架网络
```

NCCL 根据 topology 选择 ring/tree/channel 和传输路径，但程序仍要把高频、大流量 collective 放在更快通信域。例如 tensor parallel 通常限制在单节点；pipeline 的点对点激活更适合跨节点。

## 5. PyTorch Distributed 关键语义

### 5.1 Collective 是原地且异步可选

`dist.all_reduce(tensor)` 通常原地修改 tensor。`async_op=True` 返回 work handle；只有在真正使用结果前 `wait()`，才能与计算重叠。过早 wait 等于没有 overlap，过晚使用则产生数据竞争。

### 5.2 Shape/dtype 必须一致

大多数 collective 要求所有 ranks 的 tensor 元素数、dtype 和调用顺序匹配。某一 rank 因条件分支跳过 collective 是典型 deadlock 来源。

### 5.3 多进程调试

日志应带 rank；异常要确保所有进程终止；用小 world size 和确定性输入验证。单 rank 正确并不能证明 collective 顺序正确。

## 6. Collective Benchmark

对 $M$ bytes 的 all-reduce，测得时间 $t$ 后可报告算法带宽：

$$
BW_{alg}=M/t.
$$

但 ring 实际链路流量包含系数，常换算 bus bandwidth：

$$
BW_{bus}=BW_{alg}\cdot2\frac{P-1}{P}.
$$

benchmark 需要：预热、GPU events/同步、多尺寸扫描、固定 ranks/topology、避免把 tensor 初始化计入。小消息主要比较 latency，大消息比较渐近带宽。

## 7. Data Parallelism（DP）

### 7.1 数学等价

全局 batch $B$ 分到 $P$ ranks，每个 rank 处理 $B/P$：

$$
g_r=\frac{P}{B}\sum_{i\in\mathcal B_r}\nabla_\theta\ell_i,
$$

all-reduce 后平均：

$$
g=\frac1P\sum_rg_r
=\frac1B\sum_{i\in\mathcal B}\nabla_\theta\ell_i.
$$

若每个 rank 的 loss 已做 mean，collective 后必须再除 world size；若 loss/sampler 定义不同，缩放也不同。

### 7.2 训练步骤

```text
每 rank 拥有完整模型
→ 读取不同 mini-batch shard
→ forward/backward 得本地梯度
→ 对梯度 bucket all-reduce
→ 所有 ranks 用相同梯度 optimizer.step
```

实际 DDP 在 autograd hook 中按 bucket 启动 all-reduce，使较早层的梯度通信与较晚 backward 计算重叠。bucket 太小，延迟高；太大，启动太晚。

### 7.3 优缺点

- 计算扩展简单、每 rank 大 GEMM 保持高效；
- 参数、梯度、优化器状态完整复制，不解决模型单卡放不下；
- 扩展受最大有效 batch 和梯度通信限制。

## 8. Tensor Parallelism（TP）

以两层 MLP：

$$
Y=\phi(XA)B.
$$

### 8.1 Column-parallel 第一层

按输出列分 $A=[A_1,\ldots,A_P]$：

$$
H_r=\phi(XA_r).
$$

每 rank 独立得到一部分 hidden，无需 forward 通信。

### 8.2 Row-parallel 第二层

按输入行分：

$$
B=\begin{bmatrix}B_1\\ \vdots\\ B_P\end{bmatrix},
\qquad Y=\sum_rH_rB_r.
$$

每 rank 算 partial output，再 all-reduce 求和。这样中间 hidden 一直分片，只有 block 输出同步。

### 8.3 Transformer 中的映射

- Q/K/V、MLP up/gate：column-parallel；
- attention output、MLP down：row-parallel；
- norm、残差常复制或配合 sequence parallel。

TP 不需要增大全局 batch，也没有 pipeline bubble，但每层都通信，要求高带宽低延迟，通常放在单 NVLink/NVSwitch 域。TP 过大还会让本地 GEMM 变小，计算效率下降。

## 9. Pipeline Parallelism（PP）

### 9.1 朴素 layer-wise model parallel

把连续层分给 $S$ 个 stages，单 batch 依次流过。任一时刻只有一个 stage 工作，其余等待，利用率约 $1/S$。

### 9.2 Micro-batching

把 batch 分成 $m$ 个 micro-batches，像流水线一样交错：stage 0 处理 micro-batch 2 时，stage 1 处理 micro-batch 1。只看简单 forward 或 GPipe 类 schedule，bubble 比例近似：

$$
\frac{S-1}{m+S-1},
$$

常简写 bubble/useful work 比为 $(S-1)/m$。$m$ 越大利用率越高，但会影响激活内存、通信次数和有效 batch。

### 9.3 Forward/Backward Schedule

- **GPipe**：先完成所有 micro-batch forward，再反向；简单但保存激活多；
- **1F1B**：warmup 后每个 stage 交替一次 forward、一次 backward，降低峰值激活；
- stage 必须按一致 tag/order send/recv，错误调度会 deadlock。

PP 传输的是边界激活/梯度，约与 $B\times T\times d$ 有关，而不是每步传所有参数；因此可跨较慢网络。但存在 bubble、stage 负载不均和切层复杂度。

## 10. 三种并行的本质对比

| 方法 | 切分对象 | 主要通信 | 内存收益 | 主要限制 |
|---|---|---|---|---|
| DP | batch | 梯度 all-reduce | 无参数收益 | batch 上限、梯度通信 |
| TP | 层内宽度 | 每层 all-reduce/all-gather | 参数与部分激活 | 高频通信、小 GEMM |
| PP | 层深度 | stage 间激活 P2P | 参数按 stage | bubble、调度、负载均衡 |

它们不是互斥方案：大规模训练通常 TP 放节点内，PP 跨节点使模型放下，剩余设备用于 DP。

## 11. 正确性测试

### Collective

- 用 rank 可辨识输入，手算 all-reduce/gather/scatter 结果；
- 测不同 tensor sizes 与非整除 shard；
- 检查所有 ranks 都得到期望值。

### DP

- 相同初始权重和全局 batch，与单进程大 batch 的一步参数更新比较；
- 核对 sampler 不重叠、loss scaling 正确；
- 多步后所有 ranks 参数仍一致。

### TP/PP

- 拼接/归约后的 forward 与 dense reference 比较；
- backward 的参数梯度逐块比较；
- micro-batch 合并等于完整 batch；
- 非整除维度要 padding 或明确拒绝。

## 12. 常见误区

- All-reduce 不是“发给 rank 0 再广播”的唯一实现；ring/tree 会更高效。
- collective 调用集合相同但顺序不同也会 deadlock。
- DP 的 global batch 是 per-rank batch 乘 world size 再乘 accumulation steps。
- TP 切矩阵后还要推导 backward collective，不能只验证 forward。
- PP 增加 micro-batches 不是免费：激活、通信 latency 和 batch 语义都会变化。
- 理论通信 bytes 相同不代表时间相同；消息数、topology 和 overlap 同样重要。

本讲的核心是把并行训练还原成“本地矩阵运算 + 少数 collective”。只要能逐层写出每个 rank 持有什么 tensor、何时需要什么完整结果、用哪个 collective 得到它，就能推导正确性、内存和通信成本。
