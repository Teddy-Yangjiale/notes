## 一、本讲要解决什么问题（TL;DR）

把 LLM 的能力提升从"改参数"搬到"不改参数"：在推理阶段多花算力，能否像预训练 scaling law 一样**可预测**地换到更高的正确率？本讲给出答案是肯定的——对同一道题**重复采样 K 次**，只要 K 中有一次答对（coverage），coverage 与 K 之间服从**幂律（power law）**，且这一规律在 7000 万到 700 亿参数的模型上、跨数学/代码/智能体任务都成立，连 70M 的小模型也成立。但"能生成出来"不等于"能挑出来"：在缺乏自动验证器的领域，多数投票（majority voting）在 10–50 个样本后就饱和，与理论 coverage 之间留下巨大的**生成–验证鸿沟（generation-verification gap）**。因此后半个问题变成：如何**分配推理算力**（并行重复采样 vs 串行自我修订 vs 带过程奖励模型（PRM）的束搜索），以及如何用 **Archon** 这类框架把多种推理时技术自动组合成一个"推理架构"。

## 二、核心概念与术语

- **推理时计算 / 测试时计算（test-time compute, inference compute）**：模型参数冻结、不做微调，只在推理阶段多花 token/多次调用来换取质量。重要在于它把"提升能力"这件事从少数机构能做的预训练，变成任何人都能做的工程。

- **重复采样（repeated sampling）**：对同一个问题独立采样 K 个答案。这是本讲最基础的算力杠杆。

- **覆盖率（coverage）**：K 个样本中**至少有一个**答对的问题占比，即"理论上限"。它是 pass@k 在整个数据集上的平均。

- **pass@1 / pass@k**：pass@1 是一次采样就答对的概率；对**某一道题 i**，若单次正确率为 p_i，则 pass@k = 1 − (1 − p_i)^k（**逐题是指数曲线**）。

- **幂律 scaling（power law）**：coverage C 与样本数 K 的关系，形式为带系数 A、B 的幂律（转写只说"C 是 coverage、K 是样本数、A 和 B 是通过拟合得到的系数"，未给出完整公式——**待核对**）。它是可外推的：能预测"达到某个 coverage 需要多少样本"。

- **难例长尾（long tail of hard problems）**：数据集中 pass@1 从高到低连续分布、且**极难题占相当比例**。这是幂律成立的**充分必要条件**——易题多、难题呈长尾，逐题的指数曲线叠加起来才在整体上呈现幂律。

- **生成–验证鸿沟（generation-verification gap）**：模型"能生成正确答案"的能力（coverage / oracle 选择）与"能识别出哪个是正确答案"的能力（best-of-n、多数投票）之间的差距。难题上尤其大。

- **验证器（verifier）**：判定某个候选答案是否正确的机制。形式证明（formal proofs）、单元测试（unit tests）、编译器/输出等价性比对、奖励模型都算。

- **结果奖励模型（outcome reward model, ORM）**：只看最终答案整体打分。
- **过程奖励模型（process reward model, PRM）**：对解答的**每一步**打分（0–1 之间）；步骤粒度由人定义（一句、一个"有语义的推理块"），人工标注每步好坏后训练得到。二者都是语言模型微调而来，域内最好，跨域有一定泛化。

- **并行扩展 vs 串行扩展（parallel vs sequential scaling）**：并行 = 一次生成 n 个独立答案再选；串行 = 让模型基于自己的答案**反复修订（sequential revisions）**直到满意。束搜索（beam search）是二者结合：每层用 PRM 打分剪枝。

- **推理时架构（inference-time architecture）**：Archon 的视角——把"调哪些模型、用哪些推理时技术、按什么顺序叠几层"当作一个**架构设计问题**来搜索。

- **Archon 的算子**：generation（采样 n 个）、fusion（把 k 个候选合成 1 个）、critic（挑优缺点）、ranker（排序）、verifier（打分并给出理由）、unit test generation（生成单测）、unit test evaluation（让模型评估答案是否满足单测）。

## 三、主线内容

### 1. 三阶段与范式转移（[00:05]–[12:23]）

LLM 开发分三段：**预训练**（耗时数月、大量 GPU、万亿级 token）、**微调**（数据量比预训练少几个数量级）、**推理**。过去的钱几乎全砸在预训练上，"每次推理调用几乎不花钱"——因为它只是用户与模型之间一次来回。新范式是：可以在推理上花大量算力，而且这部分算力可以**离线跑**——把 agent 放出去解题，让它一直生成 token、持续改进答案质量。

### 2. Large Language Monkeys：重复采样（[01:06]–[11:20]）

设定：一个问题 → 重复问同一个模型 10 次、100 次、1000 次 → 用一个 verifier 挑出正确的那个作为系统输出。

- 意义：单次尝试不如 GPT-4o 的弱势模型（转写识别为 "llama 3 8B or 7P"，应为 Llama-3 8B / 70B——**待核对**），通过重复采样 + 选对，可以显著超过更大更强的闭源模型。
- 适用域广，包括 **SWE-bench**（转写识别为 "bbench"）这类**智能体基准**：模拟软件工程师改代码、打 patch。
- 具体数字：在 SWE-bench 类任务上，横坐标样本数从 1 到 **1000**，DeepSeek（讲师说"I believe this was the DeepSeek V3 model"）在 **1000 个样本后**能解决比 **Claude 3.5 / o1-preview**（**待核对**）更多的编码与软件工程问题。因为有单元测试可选答案，这就是一条端到端自动化地把开源模型变强的路径。
- 幂律拟合：在 Llama-3 8B/70B、Gemma、Pythia 等模型上，参数从 **70M 到 70B**，预测曲线与实测 coverage 曲线高度吻合。讲师特别强调：**70M 这种极小模型也呈现同样的 scaling 行为**。
- 为什么是幂律？逐题是指数曲线 1−(1−p)^k，但**跨题**却观察到幂律。解释：要让整体呈幂律，数据中必须存在**难例长尾**（充分必要条件）。实证检查：简单题在 pass@1 就被解决，pass@1 越低（越难）的题目数量形成一条长尾——该条件成立。

### 3. 自动验证与"生成–验证鸿沟"（[12:23]–[26:41]）

重复采样要落地，**必须有自动验证**：

- 数学：形式证明工具逐步校验。
- 代码：**单元测试**；写单测通常比写完整程序简单，且可由人写。
- **AI as a compiler**（讲师所在实验室项目）：用 LLM 把 PyTorch 源码编译成 **CUDA** 下层代码。验证天然可得——对任意输入，比较 CUDA 与源 PyTorch 输出是否一致即可。对应基准 **KernelBench**，采样数增加时 CUDA 生成 coverage 同样持续上升。讲师补充：任意**两种语言之间的翻译**（Python/C++ ↔ Java）都天然可验证等价性。

**鸿沟**（无验证器的领域）：对比曲线里，绿线 = 多数投票，蓝线 = coverage（假设有完美选择器）。多数投票在 **10 或 50 个样本后就平台化**，而 coverage 远高于此。GSM8K 上还行，但更难的 **MATH** 上鸿沟更大；换成奖励模型打分取 best-of-n、或把多种方法组合，鸿沟依然很大。

原因：最难的题目，在 **1000 甚至 10000 个样本中可能只被解出 1、2 或 3 次**。这类稀有正确答案，多数投票按定义抓不到。讲师给出资源：这个数据集——**每题 10000 个样本**——已发布在 Hugging Face 上，缩小生成–验证鸿沟是个好课程项目。

课堂讨论中值得记的几点：① 验证器质量决定这套方法的上限；② 可以先让模型"自学习/探索"收集洞察，再进入并行采样；③ 有些题判断"对"很难但判断"错"很容易，可以用排除法/演化式过滤；④ 验证器本身也可以做集成（下节课讲无监督 verifier 集成，规模是 10–20 个而不是上千个，因为算力太贵）；⑤ 对数学题人工抽查答案，正确率约 "97–98%"（转写识别为 "90 like 7 8%"——**待核对**）；单元测试本身也可能覆盖不全。

### 4. Snell et al.：并行 vs 串行，ORM vs PRM（[26:41]–[45:18]）

- **并行**：一次问 n 遍，看结果（outcome）对不对，可用 ORM 打分取 best-of-n。
- **串行**：让模型提出初始解法后**不断修订、从不同角度改进**，直到满意再输出（本讲假定靠 prompt 实现；推理模型已把这种行为训进内部）。
- **PRM 束搜索**：举例——每一层预算 4 个样本，用 PRM 打分取 **top 2**，再从这两个继续采样展开，逐层进行。
- 实验设置：**MATH 数据集，12k 训练集 / 500 道测试题，用 PaLM 模型**；自己训了 PRM，并微调了一个专门做修订的模型（讲师补：现在任何 instruction-tuned 模型只要 prompt 得当都能做修订）。按 pass@1 把题目分成 **5 个难度桶**。
- 结果观察：
  - 在"生成预算 → 准确率"图上，多数投票 < ORM（紫）< PRM（绿），最优组合（蓝）最好；但**如何混搭修订与并行仍是开放研究**——目标是在每个准确率上最小化生成预算。
  - **串行/并行比例随难度变化**：简单题上"串行 token 远多于并行"的配比（最深紫色）准确率最高；**越难越难说**，第 4 桶到第 5 桶的最优配比还会变。
  - **关键权衡**：对**简单和中等题**，增加测试时算力**比扩大预训练更划算**（推理 token / 预训练 token 比率为正）；但**对最难的题，更大的模型 / 更多预训练仍然更好**，即便给测试时算力一个很大的预算。讲师补充现实约束：不是谁都能预训练大模型，所以即便预训练理论上更优，测试时扩展对大多数人仍是最可行的路。

### 5. Archon：把推理时扩展当架构搜索（[45:18]–[62:45]）

问题形式化：输入 = 目标基准集 + **推理调用预算** + 可用 LLM 集合 + 推理时技术集合；优化器叫 **ITAS（inference-time architecture search）**；输出 = 一个把多个模型与技术拼起来的"推理架构"。

**算子效果（一个推理/问答基准上的 win rate）**：
- 左图（**同一模型**采样 1–10 个）：随机选（橙，最差）< 让模型 rank 取 top-1（绿）< **oracle 选择**（蓝）< **fusion**（红）——fusion 让模型看到全部 K 个候选后合成一个最终答案，**其质量能超过 oracle 选择**；再好一点的是先筛 top 5 再 fusion（紫）。
- 右图（**1 到 10 个不同模型**各出一个答案，按模型强弱依次加入）：同样趋势成立，说明 fusion 对异构来源的候选也有效。

**单元测试类算子**：让模型为编码/数学/推理题**自己生成单测**，更激进的是**让模型评估答案是否满足单测**（连单测都不跑）。例子：题目"检查输入字符串中圆括号是否配平"，模型生成的单测如"括号数为奇数时应输出 no"、"遇到闭括号必须匹配最近一个未匹配的开括号"，还能让模型直接写出测试代码。

**搜出来的架构**：多层结构，例如 生成层（多个不同模型）→ critic + ranker → 多个并列的 fuser → 再接 critic/ranker。为降低搜索代价，先离线确定"generation → critique → ranker → fuser"这个强序列来**缩窄搜索空间**，再用**贝叶斯优化（Bayesian optimizer）**在一个 held-out/训练数据集上，以"准确率 vs 调用次数"为目标搜索。

**约束与发现**：
- 每层只用一种推理时技术；第一层永远是 generator；**critic 必须排在 ranker 或 fuser 之前**；**单测生成器后面必须紧跟 evaluator**。
- 贝叶斯优化**优于贪心搜索和随机搜索**，配置效率（样本效率）更高。
- **"加深"有用**：例如集成多个模型 + **3 层 critique & fuser** + 最后一层 fuser 的架构，显著优于"最好的模型只调用一次"或"最好的模型调用 8 次 + 单层 fusion"。"像深度学习里加层一样，推理时加层也能变强"。

**结果（pass@1，即架构最终只输出一个答案）**：
- 只用**开源模型**就能在 pass@1 上以大幅优势匹配或超过当时的前沿闭源模型（GPT-4o、Claude 3.5 Sonnet）。
- 平均 pass@1 **提升 14.1%**，覆盖**指令跟随、推理、数学、编码**四类任务。
- 可以训练**任务专用** Archon，也可以训练**通用** Archon；通用版本同样表现很好、也超过前沿模型——说明推理时架构能**超越它被优化的有限任务集而泛化**。

## 四、论文精要

**1. Large Language Monkeys（Brown et al. 2024）**
- 贡献：系统刻画"重复采样 + 验证器"的 inference scaling law。
- 关键结论：coverage 与样本数 K 呈**幂律**；70M–70B 参数、跨数学/代码/智能体（SWE-bench）任务均成立；根源是数据集中存在**难例长尾**。
- 讲师强调：小模型"其实已经知道答案"，只是在第一次尝试时不说出来；重复采样是把这些答案**激发（elicit）并浮现（surface）**出来。SWE-bench 上 DeepSeek 采样 1000 次可超过 Claude 3.5 / o1-preview。

**2. Scaling LLM Test-Time Compute Optimally…（Snell et al. 2024）**
- 贡献：提出"按难度**最优分配**测试时算力"，并对比并行/串行/PRM 搜索。
- 关键结论：MATH 12k 训练 / 500 测试，PaLM 模型，5 个难度桶；简单题偏串行、难题配比不明确；**简单和中等题上测试时算力优于扩预训练，最难题上仍是更大的模型更好**。
- 讲师强调："这块还是未解研究"——如何混搭修订与并行、如何在给定准确率下最小化生成预算，都还没有定论；而且这是"work in progress"。

**3. Archon（Saad-Falcon et al. 2024）**
- 贡献：把推理时技术组合建模为**架构搜索问题**（ITAS + 贝叶斯优化）。
- 关键数字：开源模型组合下 pass@1 平均**超过 GPT-4o / Claude 3.5 Sonnet 14.1%**；任务专用版与通用版均有效。
- 讲师强调：fusion 的效果强到**能超过 oracle 选择**；架构"加深"（多层 critic + fuser）持续带来收益；本讲助教（TA）是论文共同作者。

**4. How Do Large Language Monkeys Get Their Power (Laws)?**
- 一句话贡献：解释重复采样的幂律**从何而来**——给出幂律成立的**充分必要条件**。
- 关键结论：逐题的 pass@k 是指数曲线 1−(1−p)^k；要让聚合后的 coverage 呈幂律，数据集中必须存在**难例长尾**；作者实证验证该条件成立。
- 讲师强调的点：讲师在 [07:15]–[11:20] 完整推导并展示了这部分内容（逐题指数 vs 跨题幂律的对比、长尾分布的直方图），但**在转写中并未点出这篇论文的标题**——本讲只在开头报了 Large Language Monkeys 一篇。此处对应关系为按内容推断，**待核对**。

## 五、讲师的关键论断（带时间戳）

- [00:05] 三阶段划分：预训练几个月、海量 GPU、万亿 token；微调数据量少几个数量级；推理——"看到各种不改模型参数就能让模型变好的方法"。
- [02:09] "模型其实已经知道这些难题的答案，重复采样只是把它们激发出来——它们只是第一次不说。"（"they just don't tell us that in the first trial."）
- [03:12] coverage 定义：至少被一个样本解决的问题占比；SWE-bench 上样本数从 1 到 1000。
- [05:14] coverage 与并行采样数 K 之间服从**幂律**（"follow an exponential power law"），可预测"达到某 coverage 需要多少样本、该分配多少资源"。
- [06:15] 该规律在 70M 到 70B 参数、多个模型族上都成立；**70M 的小模型也有同样的 scaling 行为**。
- [09:18] 幂律成立的**充分必要条件是存在难例长尾**；实证上该条件成立。
- [11:20] 范式转移：过去预训练花几亿/几十亿美元、每次推理几乎不花钱；现在可以往推理里砸算力，且**可以离线跑**——放 agent 出去一直生成 token。
- [12:23] 重复采样要能落地，"**必须有自动验证**"——否则你有一堆样本却不知道哪个对。
- [14:28] AI as a compiler：PyTorch → CUDA，"对任意输入比较两者输出是否一致"就是天然完美验证器；KernelBench 上 coverage 随样本数持续上升。
- [16:32] 生成–验证鸿沟：多数投票在 **10 或 50 个样本后就平台化**，与 coverage 差距巨大，难题（MATH vs GSM8K）上更明显。
- [17:32] 最难的题目在 1000–10000 个样本中**可能只被解出 1、2 或 3 次**——多数投票从定义上抓不到。
- [26:41] 测试时扩展有两种：**并行采样**与**串行修订**（让模型不断修改、从不同角度看，直到有信心再输出）。
- [30:49] PRM 束搜索示例：每层预算 4 个样本，用 PRM 打分取 **top 2** 再展开。
- [37:59] **简单和中等题，加测试时算力比扩预训练更划算；最难题上，更大的模型仍然更好**——即便给测试时算力一个很大的预算。
- [40:03] 现实约束："不是所有人都能预训练大模型"，所以即使预训练理论上更好，测试时扩展对大多数人仍是最可行的路径。
- [53:30] **fusion 的效果能单独超过 oracle 选择**：把所有候选呈现给模型让它合成一个答案，比"用完美验证器挑出最好的那一个"还要好；先筛 top 5 再 fusion 更好。
- [58:35] 架构**加深**有用：3 层 critique + fuser + 最终 fuser 的集成架构，显著优于"最好模型调用一次"和"调用 8 次 + 单层 fusion"——"像深度学习加层一样，推理时加层也能变强"。
- [61:44] 只用开源模型，Archon 在 pass@1 上**平均超过 GPT-4o 或 Claude 3.5 Sonnet 14.1%**；通用版 Archon 也能做到，说明推理时架构可**跨任务泛化**。

## 六、动手启示

1. **先问"这道题有没有验证器"，再决定要不要做重复采样。** 有形式证明、单元测试、输出等价性比对、可编译/可执行反馈的领域，重复采样 + 验证是端到端自动、可扩展的；没有验证器的领域，先投入做验证器，收益通常大于继续加样本。

2. **用 1−(1−p)^k 做预算估算，但记住它只对单题成立。** 整体 coverage 是幂律、会随难度长尾递减；先在小规模（如 K=8/16）估出 pass@1 分布，判断你的任务是否有难例长尾——长尾越重，加样本的边际收益越好。

3. **样本数到 10–50 之后，别再指望多数投票。** 它在这个量级就饱和了；要继续吃 coverage，必须换更强的选择机制：ranker / fusion / critic / PRM 束搜索，或者让模型自己生成单元测试并评估。

4. **优先试 fusion，而不是只做 best-of-n。** 把 K 个候选直接呈现给模型让它合成最终答案，在 Archon 的实验里能超过 oracle 选择；"先筛 top-k 再 fusion"比"全部 fusion"更好。

5. **按难度分配串行/并行比例。** 简单题给更多串行修订预算（自我修正），难题加大并行探索；不要对所有题用同一套配置。更省事的做法是像 Archon 一样，把配比交给贝叶斯优化在 held-out 集上搜（约束：critic 在 ranker/fuser 之前，单测生成器后必须接 evaluator）。

6. **异构模型 ensemble + 多层 critic/fuser 是便宜的加成。** 多个开源模型各出一答案，再用 ranker/fuser 合成，往往比堆单模型的采样次数更划算；架构"加深"的收益在本讲多个任务上都被验证。

## 七、遗留问题与开放挑战

1. **生成–验证鸿沟怎么缩小？** 讲师明确把它列为"适合本课程的研究项目"，并提供了 Hugging Face 上每题 10000 样本的数据集。无验证器领域（物理仿真、机器人、动态模拟等）尤其难。
2. **如何最优地混搭并行与串行（含树搜索/束搜索）？** 讲师直接说"这是仍然开放的研究问题"（"this area is still unopen research"），目标函数应是"给定准确率下最小化生成预算"。
3. **难题上的最优串行/并行比例没有定论**：从难度第 4 桶到第 5 桶，最优配比会变化，"很难说清到底是串行还是并行更好"。
4. **预训练 vs 测试时算力的边界仍未定**：讲师强调这是 "still work in progress"，且现实约束（不是所有人都能预训练）使得这个比较在实践上更加复杂。
5. **验证器本身的质量与集成**：验证器可能不准（用自身模型做验证会有偏差）；能否生成上千个验证器再做多数投票？讲师回应为可行的研究方向，但**算力极其昂贵**，他们只做到 10–20 个的无监督集成（下节课内容）。
6. **验证覆盖率本身也可能是假的**：编码任务的单元测试可能覆盖不全；数学题人工抽查也有约 2–3% 的判定误差（数字待核对）。
7. **Archon 的搜索代价**：完整搜索需要极大量的推理调用，只能靠离线预处理（如先固定 generation→critic→ranker→fuser 序列）大幅裁剪搜索空间，这是当前方法的实际瓶颈。
