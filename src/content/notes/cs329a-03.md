## 一、本讲要解决什么问题（TL;DR）

上一讲（推理时扩展 / inference-time scaling）留下一个悬案：重复采样（repeated sampling）能把正确解"采样出来"，但模型的 **覆盖率（coverage）上升、单次选对的能力却很快饱和**——这就是生成-验证差距（generation-verification gap）。本讲的主题就是：**如何自动地把那个正确解从一堆候选里挑出来，并在生成过程中引导模型**。核心方法论是训一个验证器（verifier）给候选解打分。四篇指定阅读构成一条清晰的历史脉络：从"只判断最终答案对不对"（ORM，2021），到"逐步判断每一步对不对"（PRM，2023），再到"用模型自己 rollout 自动生成逐步标签、无需人工标注"（Math-Shepherd，2023），最后到"根本不训新验证器，而是用推理算力把一个现成的弱验证器池聚合成强验证器并蒸馏到极小模型"（Weaver，2025）。讲师反复强调的结论是：过程奖励（PRM）整体优于结果奖励（ORM）且更能抑制假阳性（false positive），但工程上最好**两者结合**；而验证器真正值钱的地方在于——**它不改动基座模型，基座保持通用，验证器负责引导**。

## 二、核心概念与术语

| 术语 | 一句话定义 | 为什么重要 |
|---|---|---|
| 验证器（verifier） | 输入"问题 + 候选解"，输出该解正确性的概率/分数的模型 | 把"能生成正确解"转化为"能选出正确解"的唯一杠杆；既是推理时的选择器，也是 RL 的奖励来源 |
| 结果奖励模型（outcome reward model, ORM） | 只对整个解的最终答案正确性打分（本讲中转写常简写为 OM） | 训练数据便宜（只需最终答案对错），但对"推理全错、蒙对答案"的假阳性无能为力 |
| 过程奖励模型（process reward model, PRM） | 对解的**每一个中间步骤**单独打分 | 能做细粒度信用分配（credit assignment），显著压制假阳性，且更抗分布漂移 |
| 结果监督 / 过程监督（outcome supervision / process supervision） | 训练信号来自"最终答案对错" vs "每一步对错" | 决定了验证器能看到多少信息量，也决定了标注成本 |
| 生成-验证差距（generation-verification gap） | 模型"能采样出正确解"与"能识别出哪个是正确解"之间的落差 | 自我改进闭环的真正瓶颈；不缩小它，采样再多算力也是浪费 |
| best-of-n / 重复采样选择 | 采样 n 个候选，用验证器打分取最高分那个输出 | 验证器最直接的落地形态，本讲所有实验的评测协议 |
| 多数投票（majority voting）/ 自一致性（self-consistency, SC） | 不用任何奖励模型，取出现次数最多的答案 | 本讲所有实验的基线；讲师在第 2 讲已指出它在约 10–50 个样本后失效 |
| 弱验证器（weak verifier） | 与真实标签**相关但不完美**的验证器 | Weaver 的关键前提："弱"不是说故意选差的验证器，而是**没有哪个验证器是完美的** |
| 验证器集成（verifier ensembling） | 把多个（不同实验室、不同数据训出的）验证器加权聚合成一个更强的验证器 | 用推理算力而非训练来缩小生成-验证差距 |
| 弱到强监督（weak-to-strong supervision） | 用少量标签估计各弱验证器的准确率，再组合出强信号（受 Snorkel 启发） | 只用 1% 标签就能逼近全监督集成效果 |
| LLM-as-a-judge | 直接 prompt 大模型"你觉得这个答案对吗"，或配工具/评分细则打分 | 除 PRM、ORM 之外的第三类验证器，无需训练 |
| PRM 数据标注成本 | PRM 需要 K 个解 × 每个解若干步 的逐步标签 | PRM 落地的最大障碍，直接催生了 Math-Shepherd 的自动标注 |
| 奖励黑客（reward hacking） | 生成器学会钻验证器打分的空子（如跳过推理直接给答案） | 一旦把 PRM 用于 RL/微调生成器就必须设防 |
| 信用分配（credit assignment） | 把最终成败归因到具体哪一步 | PRM 相对 ORM 的核心优势 |

## 三、主线内容

### 3.1 开场：验证是推理时扩展的下半场 `[00:05]`

讲师承接上一讲：语言模型"似乎知道"很多难题的答案，尤其在重复采样等测试时技术下能生成出来；但**问题是如何自动选出哪一个是对的、或在整个生成过程中引导模型**。这就是验证。本讲的四篇论文展示了"我们对待验证的方式如何随时间演变"。

### 3.2 第一篇：GSM8K 与第一个结果级验证器 `[01:07]–[20:43]`

**动机**：LLM 会幻觉，会自信地向用户输出错误解法——"四年后的今天依然如此，只是模型已经好太多了"。

**贡献一：GSM8K 基准。** 8,500 道小学应用题，强调三点：题目质量与多样性、**多步推理**（题目本身简单，但必须走几步才能到答案）、以及**用自然语言书写解题过程**而非纯数学式子。讲师特别指出：即使到今天，对**小模型**的评测来说 GSM8K 依然是一个非常有用的评测集，"你们做项目时也可以考虑定义这一类的 eval"。

**贡献二：训练验证器。** 验证器输出"一个解是正确的概率"。

- **数据构造**：人工只**离线为每个问题写一次**标准答案。然后让生成器对每个问题重复采样 **100 个解**，把每个解的最终答案与人工答案比对，得到 0/1 标签。于是得到 (问题, 解, 标签) 三元组。
- **架构**：验证器本身也是一个语言模型，但在其上加了一个**小的标量头（scalar head）**，在**每个 token 上**输出二分类预测；问题部分的 token **被 mask 掉**不参与优化。
- **两个损失**：① 正确性二分类损失；② 常规的**语言建模下一 token 预测损失**。论文称两个损失一起用效果更好。
- **训练流程**：先在部分数据上对生成器做 **2 个 epoch** 的微调；然后每个问题采样 **100** 个 completion并打标签；最后用这份数据训练验证器 **1 个 epoch**。
- **讲师点评**：现在的模型指令跟随和数学能力已经很强，**"这个 SFT 步骤是否还需要是有争议的"**，很多较新的验证器直接跳过 SFT，直接训验证器目标。
- **标注粒度消融**：可以在**句子级**打标签（遇到句号就判断前一句是否正确），也可以在 **token 级**打标签（token 级是个很嘈杂的标签——等于要求每个 token 都走在通往正确答案的路径上）。
- **推理时的打分**：即使每 token 都有预测，最终只取**最后一个 token 的分数**作为整个解的分数（绿=高分，红=低分）。讲师展示的两个例子：一个中间有低分但结尾转绿、判为正确；另一个"开头不错，但在生成后段犯了错"，结尾变红、判为错误，与实际标签一致。

**三组关键结果：**

1. **验证 vs 直接微调**（`[10:20]`）：对 **6B 和 175B**（GPT-3）两个规模，"采样 100 个解 + 取验证器最高分"都优于纯 SFT，**且验证器训练集越大优势越明显**。反之，数据集较小时（对 175B 来说是**少于约 1000 条**）**验证基本没有帮助**。
2. **生成器/验证器的规模配比**（`[12:24]`）：**大生成器 + 小验证器 > 小生成器 + 大验证器**。讲师的解释是"生成平均而言是比验证更难的任务"，因此这个结果符合直觉；但**寻找这两者规模的帕累托最优点（Pareto optimal）是一个非常值得做的研究方向**——尤其是现在基座模型进步巨大，HuggingFace 上还有大量现成的验证器/奖励模型和排行榜可供配对测试。
3. **测试时扩展的天花板**（`[13:27]`）：随每问题采样数增加，验证器带来的收益在 **400 左右**到顶，之后再增加（如 800）**验证器就跟不住真实分布了**。讲师特意回扣上一讲：多数投票在 **10 到 50 个样本**之间就失效了（覆盖率还在涨，但选不出正确解），而这里的验证器能把有效区间推到 400。学生追问"为什么不是持平而是下降"，讲师答：图上画的不是覆盖率，而是整个系统的输出准确率；**验证器要在 800 个解里挑最高分，它的精确率（precision）掉了**——两个很接近的解一个对一个错，在 800 个里它分辨不出来，而在 400 个里能分辨。实际系统中他们**停在 100 个样本**，因为那里收益最集中、也最稳定。

**师生问答里的两个要点**（`[19:39]`）：
- 学生问"数据量更大时微调和验证会不会再次交叉"——讲师认为**数据量大到一定程度两者会趋同**，但"验证器的美妙之处在于你没有微调基座语言模型，你没有让它变得只适配某一个数据集或某一个任务。基座生成器保持通用，然后你有一个验证器来引领它"。
- 学生问"该不该对验证器也做测试时扩展"——**会，后面的 slides 就会看到**。

### 3.3 第二篇：Let's Verify Step by Step —— ORM vs PRM `[20:43]–[37:05]`

**动机**：逐步解题时，**早期一个步骤出错就会把整条解链带偏**。

- **ORM**：给整个解一个奖励（看最终答案对错）。本论文中 ORM 的分数取 **completion 最后一个 token 的分数**（沿用了上一篇的 token 级做法）。
- **PRM**：给**每一步**一个奖励。做法：让人工标注员逐段阅读模型生成的步骤，逐步标 positive / negative / neutral。整条解的**最终奖励取各步奖励的乘积**。

**PRM 的三个核心优势**（`[24:47]`）：

1. **能显著更好地处理假阳性（false positives）**——"模型可能一路幻觉、过程全错，却蒙对了最终答案"。过程监督下因为每一步都有分数，进入这种模式的可能性小得多。讲师称这是**测试时扩展的一个陷阱（pitfall）**。
2. 鼓励**可解释的推理**。
3. 解过程是**人类认可（human-endorsed）**的，因为标签是人打的。

**PRM800K 数据集**：开源的 **800K 步级标签**数据集。构造技巧：让生成器逐步采样大量解，然后**优先挑"convincing wrong-answer"样本给人类标注**（⚠️ 转写此处表述为"最终答案正确但中间步骤错误的样本"，与论文中该术语的通常含义方向相反，**待核对**），这一步使数据效率比随机挑样本**高 2.6 倍**。之后**迭代式升级 PRM**：用当前 PRM 采集数据 → 训练新 PRM → 提升数据质量。

实验基座是 **GPT-4**，ORM 和 PRM 都先对 GPT-4 做 SFT。

**举例**（`[27:53]`）："一个分数的分母比分子的 3 倍少 7，若该分数等于 2/5，求分子。"前 5 步都标为正确，最后一步算错（转写作 "X should be 15 14 but it's seven"，数字转写不完整，**待核对**；按题意正确解为 x=14）。

**结果**（`[28:55]–[30:59]`）：

- **PRM > ORM > 多数投票**（图中蓝=ORM，橙=PRM）。此图中多数投票在约 **100 个样本**后失效。
- PRM 能捞到**极稀有的正确解**——在正确率**不到 5%** 的问题分布上仍能识别正确解。
- **PRM 更省样本（more sample-efficient）**：PRM 和 ORM 都随标签增多而变好，但 PRM 的样本效率更高。（转写中"ORM 每问题 100 个标签 ≈ PRM 每问题 1 个解"这句表述含混，**待核对**。）
- **泛化性**（`[30:59]`）：跨新领域/新数据集时，**多数投票比 ORM 泛化得更好**，但 **PRM 整体优于多数投票**，且**比多数投票能容忍大得多的分布漂移（distribution shift）**。

**PRM 的风险与局限（师生问答，`[32:00]`–`[37:05]`）**：

- 学生问"某一步看起来好、但其实对最终答案没贡献"，PRM 会不会产生错误的信用分配、哪些领域会受害？讲师答：**现实是较新的方法把 PRM 和 ORM 结合起来用**，以兼取两者之利。另外一个代价是：**你为 PRM 设定的阈值成了一个新增的超参数**，必须针对你的系统去调，这是额外的复杂度。
- **奖励黑客问题（重点）**：学生问，如果模型跳过推理、直接从"设分子为 x"跳到"x=14"，PRM 怎么防？讲师区分了两种场景：
  - **只在推理时用验证器**：PRM 打分时能看到"问题 + 之前的步骤 + 当前步骤"；而且**你并没有改动生成器**，仍然可以 prompt 它一步步推理，验证器只负责打分。
  - **用 PRM 去训练/RL 生成器**：这才是真正的失效模式——**模型可能停止推理、直接产出 PRM 喜欢的最终答案**。此时必须小心，确保 CoT 本身讲得通。
  - 为什么人类标签能部分缓解：如果某一步跳过了必要的推理，人类会说"这步说不通"，把分数压低。**"这里的标签是人类打的"**——而下一篇文章的标签不是人打的，**这就是一个明确的 caveat**。

### 3.4 第三篇：Math-Shepherd —— 自动标注逐步标签 `[37:05]–[51:26]`

**动机**：PRM 潜力大于 ORM，但**需要海量数据、且很难采集**。能否把 PRM 的标签采集自动化？论文有两部分贡献：**自动标注**，以及**把奖励模型引入生成器优化的 RL 闭环**。

**核心定义**：**一个推理步骤的质量 = 该步骤到达最终正确答案的潜力（potential）**。做法是：停在某一步，从这一步往后 **rollout 采样 n 条续写**，看有多少能走到正确最终答案。两种估计：

- **硬估计（hard estimation）**：n 条续写中**只要有任意一条**到达正确最终答案，该步就标为成功（1）；否则为 0。
- **软估计（soft estimation）**：n 条续写中**到达正确最终答案的比例**（如 2/3）。

示例：n=3，从当前步采样 3 个候选步骤并续写到底，硬估计 = 1，软估计 = 2/3。

**这个方法论的四个缺陷（课堂上由学生提出 + 讲师补充，`[41:09]`–`[43:12]`）**：

1. **罕见/非主流解法会被误杀**：如果 n=3 时根本没采到那条正确轨迹，这个有效的步骤就被打了 0 分；可能需要 n=100 才看得到。
2. **难题上拿不到任何信号**：难题上绝大多数采样都是错的，软硬估计都接近 0，学习信号为零。
3. **中间步骤错、但最终蒙对**，那些错步仍会被标成"正确"。讲师的期望是"采样更多时，错误会在某条轨迹里暴露出来"，**但这没有保证**。
4. 前提：必须**已经拥有这些问题的最终答案标签**。

**验证 + RL 流程**（`[43:12]`–`[47:21]`）：

- 推理时：采样 N 条候选解 → 用 PRM 打分 → 取 PRM 分数最高者。
- 训练时：把 PRM 当奖励模型，做 RL（**Mistral 7B + PPO**）鼓励模型产出更高分的步骤。
- **硬 vs 软**：增大 n 时软估计看起来更好；但在 **n=4**（采集标签时的续写深度）时两者都达到最佳结果，**最后他们选了硬估计，因为它更好测**。
- **结果**：自一致性（SC，红）/ ORM（蓝）/ Math-Shepherd 的 PRM（绿）——Math-Shepherd 最优，且**全程零人工标注**。它还**超过了上一篇的 PRM800K 验证器**，在比 GSM8K 难得多的 **MATH** 上**提升幅度（delta）更大**。跨模型一致（Llama-70B、Llemma 34B（转写 "LMAD 34B"，**待核对**）、DeepSeek 67B）在 GSM8K 与 MATH-500 上均显著优于自一致性基线。
- RL 效果：用自家 PRM 做 PPO 明显优于只用 ORM 做 RL，但**这个提升幅度比单纯做测试时扩展要小一些**。再往上叠 RL + PPO + 验证会继续变好，但**看起来在某个点就饱和（plateauing）了**。
- 讲师总结这条路径的意义："**多个层次上都在用模型自己给自己生成数据、生成 RL 奖励信号**"。

**师生问答（`[48:22]`–`[51:26]`）**：

- 学生问能否让 PRM 激励**自我纠错（self error correction）**：可以——给模型一份**评分细则（rubric）/ 规则集**作为打分依据，让模型拿细则去检查每一步；或者**让模型用工具**，比如那道分数题如果允许用计算器就能轻松解对。**工具使用、测试时扩展、agentic 方法都能给验证过程带来更多监督信号**。
- 学生问**有没有控制测试时算力**：讲师表示不确定他们在 process vs outcome 对比时做了控制，"这在固定算力下怎么分配（生成器多采样 vs 验证器多采样）是个可以研究的问题"。另一个方法论坑：**ORM 和 PRM 必须来自同一份数据才能做苹果对苹果的比较**；你自己训 PRM、别人训 ORM 就没法比，**训练数据的影响非常大**。
- 学生问为什么 RL 之后仍用 **greedy decoding**（转写作 "3D decoding"，**待核对**）评测、没有再叠加温度采样和测试时扩展：讲师说这是**他们没做的事**；该图中"无验证"那条只用了 RL 训练，而验证那条是**对 256 个输出做的**。进一步可以做的：从这个 RL/PPO 模型出发，重新采集标签、再训一轮验证器。

### 3.5 第四篇：Weaver —— 用弱验证器缩小生成-验证差距 `[51:26]–[66:42]`

**思路的转向**：这篇 **2025 年斯坦福的新论文完全不训新验证器**，而是问：能不能**用推理算力（inference compute / inference scaling）**、特别是**用一个验证器集成（ensemble）**来缩小生成-验证差距？

- **"弱"的含义**（`[52:27]`）："我们不是故意选差的验证器——这些都是当下最好的验证器，但我们用一个集成把它们合成一个能力强得多的验证器。""弱"= **没有哪个验证器是完美的**，它们与真实标签**相关但有缺陷**。
- **三类验证器**：PRM、ORM、以及 **LLM-as-a-judge**（直接问"你觉得这对吗"，或让模型用工具/评分细则打分）。第三类是"在 PRM 和 ORM 之上的一整类验证器"。

**第一步：验证器集成与加权（`[53:28]`–`[55:30]`）**

- 参与集成的验证器可以是**不同实验室、不同数据集**训出来的，统一抽象成"输入 query、输出一个分数"的模型。
- 在**四个数据集**上比较 **top-1 / top-5 / top-10** 验证器（按某种排序取前 k 个）：**朴素地把它们集成起来总体是提升的，但并不是单调的**。
- **真正总能带来提升的，是"学一个把它们加起来的方式"**——即为每个集成成员学一个权重。方法极简：**朴素贝叶斯（Naive Bayes）或逻辑回归（logistic regression）**，就是给每个验证器加一个标量权重。只要有**一份带标签的训练集**（例如 MATH-500 的那份），就能学出权重并用到测试数据上——"就这个简单的操作，看起来带来了非常大的提升"。

**Weaver 的三步法：Score, Weight, and Select（`[55:30]`）**

1. **Score**：跑所有验证器拿到分数，**归一化到同一尺度**；并**过滤掉低质量验证器**——只要极少量标签就能判断"这几个验证器在我的标签上太差"并把它们踢出池子。讲师强调这是**非常关键的一步**：**验证器必须超过某个质量门槛才有资格进入验证器池**。
2. **Weight**：拿到各验证器的分数（0/1 或正确性的 log prob），用**弱监督（weak supervision）在极小标注数据上估计各验证器的准确率**。
3. **Select**：用这些权重组合各验证器的输出，给出一个最终分数并据此选择。

**弱到强监督的数学（`[56:30]`–`[59:32]`，受 Snorkel / Alex Ratner 等工作启发）**：

- 设定：**n 个 query，每个 query 生成 k 个解，共 m 个验证器** → 总共 **n × k × m** 个标签。目标是估计 P(第 i 个 query 的第 j 个样本是正确的 | 所有验证器给出的所有标签)。
- **关键假设：每个验证器捕捉的是"正确性"的一个相互独立的侧面。** 讲师给出的直觉："如果你的验证器池里所有验证器对任何样本都给出一样的分数，那你从它们身上什么新东西也学不到——**信号在于这一整组验证器彼此之间的相似与不相似**。"
- 基于该假设可以写出两组方程：第一组来自"任意两个验证器 i、j 相互独立"；第二组只是概率的基本运算、不含任何假设。由这两组方程定义优化问题，解出每个验证器的权重。
- 相比朴素集成，**提升在 GPQA Diamond、MATH、MMLU-Pro 这些相对困难的问题上最显著**：GPQA 的基线本来就低，但这种弱到强聚合相对朴素集成拿到了**大幅提升**。

**扩展验证算力的四种方式（`[59:32]`）**：① 采样更多解（10 → 100 → 1000）；② 生成和验证都用更大的模型；③ **增加验证器池里的验证器数量**；④ 其他分配 FLOPs / 推理算力的方式。

**主结果图（`[60:32]`）**：

- 深红虚线：**pass@k oracle**——假如有个能直接给出正确答案的 oracle 选择器（我们没有，所以才要训验证器）。
- 紫色：**supervised**——假设有大量标注数据来学权重。
- 蓝色：**unsupervised**——每个数据集只用 **1% 的训练标签**。
- 橙色：**naive ensemble**——直接平均各验证器，不做特殊处理（但仍然做了过滤、只保留好的验证器）。
- 以上全部**显著优于多数投票（majority voting）和多智能体验证（multi-agent verification, MAV）**。MAV 就是"prompt LLM 让它按若干不同方面给一个回答打分"的评分细则式方法——**它并不比多数投票好，在其中两个用例里甚至更差**。

**跨模型档位的跨越（`[61:34]`–`[63:39]`）**：

- 在这些难题上，准确率能从**略高于 40% 拉到超过 70%**，**追平 o3-mini 这个量级的模型**。
- **用 Llama-3.1-8B-Instruct 作生成器 + 一个全部 ≤8B 的验证器池**，在这些数据集上取得 **平均 70%**；"我们相当于只靠推理扩展和验证器，就把这个 8B 模型做到了和 **70B 档**差不多的水平"（转写作 "7TB class"，按上下文推断为 70B，**待核对**）。
- 讲师特别提示方法论差异：**这里报的是整个系统的最终解题准确率（solution accuracy），不是覆盖率（coverage）**——和上一讲多数投票那张图不是一回事。
- 同样的生成+验证流程用在 **70B 档模型**上，平均准确率 **86.2%**，与 **o3-mini**（闭源、更高档次的模型）非常接近。

**验证成本与蒸馏（`[64:40]`–`[65:40]`）**：

- 集成验证器的痛点：每评估一个解都要跑一大堆模型，而你有 100 个解、每个都要打分，**成本暴涨**。
- 解法：**先训一次 Weaver，然后把它蒸馏进一个小得多的模型**——可以小到 **4 亿参数（400M）**，而原来的验证器池在 **70B** 量级。
- 效果：蒸馏模型**保留了大验证器池 97% 的准确率，同时在测试时少用 99%+ 的算力**（转写为 "99 plus% use less compute"）。蒸馏版和原版都已开源、checkpoint 可用，可用于 agentic 或测试时扩展项目。
- 效率图（浅蓝=蒸馏版，深蓝=原版 Weaver，横轴=总推理算力）：蒸馏版显著更高效；**但即使是不蒸馏的原版 Weaver，因为它能达到更高的准确率水平，在那个水平上它反而比朴素集成和多数投票更省 FLOPs**。

### 3.6 课堂收尾 Q&A `[66:42]`–结尾

四篇论文串起了约四年里验证研究的演进。**结语要点**：验证能同时改善训练期和推理期的产出质量；**过程奖励非常有用、整体比结果奖励更有效，但也许需要把 PRM 和 ORM 结合起来才能得到最好的结果**；Math-Shepherd 说明"你需要大量数据，喂给验证器的数据越多它就越好，而且可以把它用在 RL 微调里提升生成器"；Weaver 走了完全不同的路——**在验证器集成上做弱监督优化，以一种"引入更多验证器"而非"对单个验证器多采样"的方式做测试时扩展**，并且可以蒸馏、用很小的模型捕获大部分质量。

四个有价值的学生提问与讲师回答：

1. **数学/推理之外还有什么领域可做验证**（`[67:44]`）？**代码（coding）**是一个非常有意思的领域（部分 benchmark 里已含编程题）。讲师预告将讲 **CodeMonkeys**：不是直接训验证器，而是**让模型造出一套测试时系统去生成单元测试，那些单元测试本身就成为你的验证器**——完全不同的路子。这类验证对**任何推理类任务**都应该有用。
2. **对已经把推理内化的推理模型，生成-验证还有用吗**（`[68:46]`）？**依然有用**。推理模型的做法本身就是：生成推理步骤 → 给奖励 → 跑 RL 循环 → 产出正轨迹 → 作为下一轮训练数据。**测试时扩展天然被用来生成训练数据**。此外它们仍能受益，因为更多采样能让它们探索解空间的不同区域。
3. **未来会不会收敛到"重复采样只用来造训练数据、推理时只问一次"**（`[70:50]`）？"**这是我们希望去的方向**"——我们希望模型 **pass@1** 就足够好，这样效率最高。**但一个挑战是：如果训练把模型在单一答案上的 log prob  sharpen 得太厉害，解的创造性和多样性可能会在训练中丢失**。而我们其实仍然喜欢模型在思考方式上保持大量创造性与多样性——"这是我们希望模型具备的好特性"。
4. **生成器和验证器架构差异大不大要紧吗**（`[71:51]`）？比如验证器是生成器的迷你版 vs. 完全不同的架构。"这是个好研究问题"。一般来说，**模型更"喜欢"自己的生成和自己的解读方式，胜过使用另一族模型**。后面会讲一篇关于某些模型能从"不同于自身的某一类验证器"中获益的论文。但讲师**没有见过专门研究"同尺寸同族 vs. 不同尺寸不同族"这种配比如何改变模型行为的研究**——这是个明确的空白。

## 四、论文精要

### 1. Training Verifiers to Solve Math Word Problems（Cobbe et al., 2021, arXiv 2110.14168）

- **一句话贡献**：提出 GSM8K 多步数学推理基准，并证明"采样 100 个解 + 训一个验证器选最高分"优于直接微调。
- **关键数字**：8,500 道小学应用题；每问题采样 **100** 个解；生成器 SFT **2 epoch**，验证器训练 **1 epoch**；6B 与 175B 两档都成立；**175B 上验证器训练集少于约 1000 条时验证不带来帮助**；收益在约 **400 个样本**处饱和（实际系统停在 **100**）。
- **讲师强调的点**：（a）验证器 = LM + **per-token 的标量头**，**问题 token 被 mask**，**二分类损失 + 语言建模损失**双目标；（b）整条解的分数取**最后一个 token**；（c）**SFT 这一步今天可能已经不必要**；（d）**大生成器 + 小验证器 > 小生成器 + 大验证器**，其帕累托最优点是开放研究方向；（e）**验证器的价值在于不动基座模型、保持其通用性**。

### 2. Let's Verify Step by Step（Lightman et al., 2023, arXiv 2305.20050）

- **一句话贡献**：系统对比结果监督（ORM）与过程监督（PRM），发布 **PRM800K**（80 万步级标签），证明 PRM 在准确率、样本效率和分布漂移鲁棒性上都更优。
- **关键数字/设置**：800K 步级标签；逐步标签为 positive / negative / neutral；整条解奖励 = **各步奖励之积**；优先标注 "convincing wrong-answer" 样本带来 **2.6 倍数据效率**；基座 **GPT-4**（ORM 和 PRM 都先 SFT）；PRM 能识别**正确率 < 5%** 的稀有正确解；此图中多数投票约在 **100 样本**后失效。
- **讲师强调的点**：（a）**过程监督最核心的好处是能管住假阳性**——"推理全错却蒙对最终答案"是测试时扩展的一个陷阱；（b）**多数投票的泛化性好于 ORM，但 PRM 又好于多数投票，且能容忍大得多的分布漂移**；（c）**现实中最新的做法是把 PRM 和 ORM 结合**；（d）**PRM 阈值是一个新增超参数**；（e）最大隐患是**用 PRM 训练生成器时的奖励黑客**（模型停止推理、直接吐 PRM 喜欢的答案），人类标签能部分缓解。

### 3. Math-Shepherd（Wang et al., 2023, arXiv 2312.08935）

- **一句话贡献**：把 PRM 的逐步标签采集**完全自动化**——用"该步能走到正确最终答案的潜力"定义步骤质量，并把得到的 PRM 直接用作 RL 奖励去提升生成器。
- **关键数字/设置**：硬估计（任一 rollout 成功即标 1）vs 软估计（rollout 成功比例）；**n=4** 时效果最好且软硬差别不大，**最终采用硬估计**；零人工标注；在 **MATH**（明显难于 GSM8K）上**超过 PRM800K 验证器，且提升幅度更大**；在 GSM8K 与 **MATH-500** 上对 Llama-70B / Llemma-34B / DeepSeek-67B 均优于自一致性；**Mistral 7B + PPO** 用自家 PRM 做 RL 明显优于只用 ORM。
- **讲师强调的点**：（a）这个自动标注的**三个硬伤**——罕见解法被误杀、难题上零信号、中间错步因最终蒙对而被标正确；（b）"**多个层次上都在用模型自己给自己生成数据和 RL 奖励信号**"；（c）**RL 带来的提升比单纯测试时扩展小一些，且优化会饱和**；（d）**该篇没有做的事情**：控制测试时算力、RL 后继续叠加温度采样与测试时扩展。

### 4. Shrinking the Generation-Verification Gap with Weak Verifiers（Weaver，2025, arXiv 2506.18203）

- **一句话贡献**：不训新验证器，而是用**弱监督**给一组现成的弱验证器（PRM / ORM / LLM-as-a-judge）学权重、聚合成强验证器，并蒸馏到极小模型以压低成本。
- **关键数字/设置**：三步法 **score → weight → select**；加权方法极简（**朴素贝叶斯或逻辑回归**，每个验证器一个标量权重）；**仅用 1% 训练标签**的无监督版；Llama-3.1-8B-Instruct + ≤8B 验证器池 → **平均 70%**，追平 70B 档；70B 档 → **86.2%**，接近 **o3-mini**；难题上从**略高于 40% 提到超过 70%**；蒸馏到 **400M** 参数（原池 70B 量级），**保留 97% 准确率、省 99%+ 测试时算力**；蒸馏版与原版均已开源。
- **讲师强调的点**：（a）"**弱**"指的是**没有验证器是完美的**，不是故意选差的；（b）**质量过滤是极其重要的一步**——验证器必须超过质量门槛才准入池；（c）核心假设是**各验证器捕捉正确性的相互独立的侧面**，**信号来自验证器之间的相似与不相似**（全 agrees 就没有信息量）；（d）**MAV（多智能体/评分细则式 prompt 验证）并不比多数投票好，有时更差**；（e）这里报的是**整个系统的最终解题准确率，不是覆盖率**；（f）"**增加验证器数量**"是一种与"多采样"并列的测试时扩展维度。

## 五、讲师的关键论断（带时间戳）

- `[00:05]` 上一讲留下的问题不是"能不能生成正确解"，而是**"我们如何自动选出哪个答案是对的，或在生成全程引导模型"**（"how can we automatically select which answer is correct or guide the model throughout the process"）。
- `[11:22]` 规模配比结论：**"大生成器配小验证器，好过小生成器配大验证器"**（larger generator + smaller verifier does better than vice versa）；寻找两者的帕累托最优配比是值得做的研究方向。
- `[13:27]` 采样数天花板：**验证器的收益到 400 左右就到顶，800 时"验证器已经跟不上真实分布"**（fails to track what's best）。
- `[15:32]` 回扣上一讲：**多数投票在 10 到 50 个样本之间就失效**（覆盖率还在涨，但选不出正确解），而验证器能把有效区间推到 400。
- `[17:38]` 为什么会掉：**"验证器要在 800 个解里挑最高分，它的精确率掉了"**（the precision of the verifier drops）——两个很接近的解一个对一个错，在 800 个里分辨不出来，在 400 个里能。
- `[20:43]` 验证器的价值主张：**"验证器的美妙之处在于你没有微调基座语言模型……基座生成器保持通用，然后你有一个验证器来引领它。"**
- `[24:47]` 过程监督的头号理由：**"模型可能幻觉、过程全错，却得到了最终正确的答案"**；用过程监督能**把假阳性管得好得多**。讲师称这是测试时扩展的一个 pitfall。
- `[26:51]` 数据采集效率：优先标注 "convincing wrong-answer" 样本，比随机挑样本**数据效率高 2.6 倍**。
- `[30:59]` 泛化性排序：**多数投票比 ORM 泛化得好，但 PRM 整体优于多数投票，且比多数投票"能容忍大得多的分布漂移"。**
- `[32:00]` 关于 ORM+PRM：**"很多较新的方法把两者结合起来用"**，因为你想兼得两边的收益；代价是**PRM 的阈值成了你必须调的新超参数**。
- `[36:05]` 奖励黑客的准确定位：只在推理时用验证器没问题（"你没有改动生成器"）；**真正的失效模式是"你拿 PRM 去微调生成器，模型停止推理、只生成 PRM 喜欢的最终答案"**。
- `[39:07]` Math-Shepherd 的核心定义：**"我们把一个推理步骤的质量定义为——该步骤抵达最终正确答案的潜力。"**（the potential of the step to reach to the final correct answer）
- `[43:12]` 自动标注的固有缺陷：**难题上"你根本拿不到任何信号"**（you don't get any signal for hard problems）；另外中间错步若最终蒙对，仍会被标成正确，"这不保证（not guaranteed）"能被更多采样纠正。
- `[46:20]` 自我改进的层次：**"你用模型自己生成标注，训练 PRM，再用这个 PRM 去改进生成器——测试时和 RL 微调都用。这是多个层次地在用模型自己给自己生成数据和 RL 奖励信号。"**
- `[52:27]` "弱"的定义：**"我们没有故意选差的验证器，这些都是当下最好的验证器，但我们用一个集成把它们合成一个能力强得多的验证器。"**
- `[55:30]` 集成的准入质量门槛：过滤低质量验证器是**"非常关键的一步"**——**"你的验证器必须超过某个质量，才有资格被放进验证器池。"**
- `[57:32]` 独立性的直觉：**"如果你池子里所有验证器对任何样本都给一样的分数，你从它们身上什么新东西也学不到——信号就在于这一整组验证器彼此之间的相似与不相似。"**
- `[61:34]` 结果量级：难题上从**略高于 40% 提到超过 70%，追平 o3-mini**；用 **8B 生成器 + 全部 ≤8B 的验证器池做到平均 70%**，相当于"把 8B 模型做到和 70B 档差不多"。
- `[64:40]` 成本解法：把 Weaver **蒸馏到 4 亿参数**（原池 70B 量级），**保留 97% 准确率、省 99%+ 测试时算力**；蒸馏版与原版均已开源。
- `[70:50]` 对未来的判断与保留：**"这是我们想去的方向——希望模型 pass@1 就足够好"**，但**"如果训练把模型在单一答案上的 log prob 磨得太尖，解的创造性和多样性可能会丢失"**，而多样性是我们想要的模型特性。

## 六、动手启示

1. **先建立验证器准入的质量门槛，再谈集成。** Weaver 的经验里，"过滤掉低质量验证器"被讲师称为非常关键的一步——只需要**极少量（哪怕 1%）的标签**就能判断哪些验证器在你的任务上太差，把它们踢出池子。聚合之前先做这道筛。
2. **加权聚合的起点要极简。** 别一上来就训复杂聚合器：先试**每验证器一个标量权重的朴素贝叶斯或逻辑回归**，归一分到同一尺度后加权。这在四个数据集上都带来了"非常大的提升"，是性价比最高的基线。
3. **ORM 与 PRM 同时上，并警惕 PRM 阈值变成新超参。** 讲师明确说"较新的方法把两者结合起来"。同时记住：用 PRM 时你引入了一个需要针对系统调的阈值超参数。
4. **只在推理时用验证器是安全的；一旦拿它去 RL/微调生成器，必须防奖励黑客。** 具体的防御手段包括：给模型一份 **rubric / 规则集**当打分依据、允许**工具使用**（那道分数题允许用计算器就能解对）、以及确保 CoT 本身讲得通。
5. **把"增加验证器数量"当作与"多采样"并列的扩展维度，并用蒸馏压成本。** 算力分配上不要只想"多采样"：更大的生成/验证模型、更多验证器都是选项。若集成成本失控，按 Weaver 的路子**训一次再蒸馏到极小模型**（400M 保留了 97% 准确率）。
6. **做对比实验时的两个方法论坑：** ① **ORM 和 PRM 必须来自同一份训练数据**才能苹果对苹果；② 报指标时说清楚是**覆盖率（coverage）还是整个系统的最终解题准确率**——Weaver 那张图报的是后者，和多数投票那张图不是一回事。
7. **任务选择上不要只盯数学。** 讲师点名**代码**是最值得做的验证领域之一， paradigms 可以是"让模型生成单元测试、用测试当验证器"（CodeMonkeys）；任何推理类任务都应适用。

## 七、遗留问题与开放挑战

1. **验证器有效区间为何会倒退。** 为什么从 400 到 800 个样本时准确率不是持平而是**下降**？讲师的定性解释是"验证器在更大候选集上精确率下降、分辨不出相近的一对解"，但**没有量化模型或明确的修正方法**（`[17:38]`）。
2. **生成器与验证器的规模/架构帕累托前沿。** 已知"大生成器 + 小验证器 > 反向"，但**最优配比是多少、以及"同尺寸同族 vs. 不同尺寸不同族"会如何改变模型行为，讲师明确表示没有见过这方面的研究**（`[13:27]`、`[71:51]`）。后者是**讲师点名的空白**。
3. **固定算力下如何在"生成器多采样"和"验证器多采样"之间分配。** 讲师在讲 Math-Shepherd 时承认**论文没有控制这一变量**，并直接把它抛给学生当研究问题（`[49:24]`）。
4. **自动步骤标注的三个未解缺陷**：罕见/非主流解法被低 n 的 rollout 误杀；难题上软硬估计都给不出信号；中间错步因最终蒙对而被标为正确——后者的纠正"没有保证"（`[41:09]`–`[43:12]`）。
5. **PRM 的信用分配何时会帮倒忙。** "某一步看起来好、其实对最终答案无贡献"导致的错误信用分配——讲师没有回答"哪些领域 PRM 会受害"，只说实践中把 ORM 和 PRM 结合使用（`[32:00]`）。
6. **优化会饱和。** Math-Shepherd 上"RL + PPO + 验证"叠满后，**曲线看起来在某个点 plateau 了**；讲师也没有解释原因（`[47:21]`）。
7. **未做的实验**：Math-Shepherd **在 RL/PPO 之后没有再叠加温度采样与测试时扩展**，也没有"从 RL 后的模型出发重新采集标签、再训一轮验证器"的迭代——这是讲师明确指出的可扩展方向（`[51:26]`）。
8. **测试时扩展的终局与多样性代价。** 未来是否会收敛到"重复采样只用于造训练数据、推理时只问一次"？讲师说这是想去的方向，但**明确担心"把 log prob sharpen 得太厉害会丢掉创造性和多样性"**——如何在提升 pass@1 的同时保住多样性，是未解张力（`[70:50]`）。
9. **Weaver 独立性假设的适用边界。** "每个验证器捕捉正确性的一个独立侧面"是整套弱到强推导的**关键假设**；当验证器高度相关（例如同源蒸馏/同数据训练）时这个假设会失效到什么程度，本讲未展开（`[57:32]`）。
10. **验证在非数学领域的形态尚未定型。** 讲师只预告了 CodeMonkeys（用生成的单元测试当验证器）这条完全不同的路子，但本讲**没有系统讨论"可验证任务 vs. 不可验证任务"的判据**，以及不可验证任务上验证器如何构造（`[67:44]`）。
