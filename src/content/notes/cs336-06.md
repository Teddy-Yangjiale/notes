## 1. 从 PyTorch 表达式到 GPU 执行

```text
Python/PyTorch graph
 → operator dispatch / compiler graph
 → CUDA 或 Triton kernel
 → blocks / warps / threads
 → PTX
 → GPU machine instructions
```

同一数学表达可对应完全不同的 kernel 数量、内存访问和同步。优化时必须把高层 API 一直追到实际 kernel，而不能只比较 Python 代码长度。

## 2. 正确性与性能必须分开验收

### 正确性

- 多种 shape、非整除边界、不同 dtype；
- 与可靠 reference 比较；
- 根据 dtype/归约长度设置 `atol`、`rtol`；
- 检查 NaN/Inf、空维度、极值和非连续输入；
- 需要时用随机种子和 property-based tests。

浮点结果一般不能要求逐 bit 等同。归约次序变化会改变舍入误差；误差界应与问题条件数、累加长度和 dtype 相匹配。

### 性能

- 同样 shape、dtype、device、layout；
- 包含相同语义和输出；
- 预热 JIT/allocator/cache；
- GPU 异步，使用 CUDA event 或计时边界同步；
- 多次重复，报告 median 和分位数；
- 性能与正确性测试都通过后才接受优化。

## 3. Benchmark 与 Profiler 的分工

**Benchmark**回答“端到端多快”：

```python
warmup()
for trial in trials:
    synchronize()
    start.record()
    fn()
    end.record()
    synchronize()
```

**Profiler**回答“时间花在哪里”：kernel 名称、launch 间隙、CPU 调度、memcpy、shape、CUDA 时间、显存和调用栈。

课件对 add、大矩阵 matmul、小矩阵 matmul 的 profile 展示了三类瓶颈：

- pointwise add 常受 HBM 带宽限制；
- 大 GEMM 可接近 Tensor Core compute-bound；
- 小 GEMM 可能由 launch latency 和低 occupancy 限制。

同一个算子名不能推断同一种瓶颈，shape 是工作负载定义的一部分。

## 4. Naive、Builtin 与 `torch.compile`

以 GeLU 为例：

$$
\operatorname{GELU}(x)\approx\frac12x
\left(1+\tanh\left(\sqrt{\frac2\pi}(x+0.044715x^3)\right)\right).
$$

若直接写多个 PyTorch pointwise operator，eager mode 可能启动多个 kernel 并产生中间 tensor。`torch.nn.functional.gelu` 可调用专门实现；`torch.compile` 则尝试捕获 graph、融合 pointwise 链并生成 kernel。

比较时要注意：

- 首次 compile 时间不能混入稳态 latency；
- dynamic shapes 可能触发重新编译；
- compiler 可能因为 graph break 无法融合；
- builtin 可能有不同 approximation mode；
- 只有 profile 能确认 kernel 数是否真的减少。

## 5. Triton 编程模型

Triton 让程序员按“program instance 处理一个数据块”思考，而不是逐 CUDA thread 手工编程。

核心概念：

- `tl.program_id(axis)`：当前 program/block 编号；
- `tl.arange(0, BLOCK_SIZE)`：块内向量化 offsets；
- `tl.load(ptr + offsets, mask=..., other=...)`；
- `tl.store(ptr + offsets, value, mask=...)`；
- `tl.constexpr`：编译期常量，用于展开和 specialization；
- launch grid：需要多少 program instances。

典型 1D kernel：

```python
@triton.jit
def kernel(x, y, n: tl.constexpr, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    values = tl.load(x + offs, mask=mask)
    result = ...
    tl.store(y + offs, result, mask=mask)
```

grid 通常为 `ceil_div(n, BLOCK)`。mask 是处理非整除边界的正确性条件，不能因为 benchmark shape 恰好整除而省略。

## 6. Triton GeLU：最简单的融合

每个 program 读取一块 $x$，在寄存器中完成乘法、立方、tanh 和缩放，再一次写回 $y$。与 eager 链相比：

```text
多 kernel：多次 HBM 读写 + 多次 launch
Triton：一次 load + 寄存器计算 + 一次 store
```

该 kernel 主要是 memory-bound。BLOCK 太小会产生太多 programs/launch scheduling；太大可能增加 register pressure。优化需跨多个向量长度测试。

## 7. Row-wise Softmax

对每行 $x\in\mathbb R^N$：

$$
m=\max_jx_j,qquad
z_j=e^{x_j-m},qquad
y_j=\frac{z_j}{\sum_kz_k}.
$$

教学 kernel 通常让一个 Triton program 负责一整行：

1. `BLOCK = next_power_of_2(N)`；
2. 读取一行，越界位置设为 $-\infty$；
3. `tl.max` 求最大值；
4. 计算指数；
5. `tl.sum` 求分母；
6. 归一化并写回。

使用 $-\infty$ 作为越界 `other`，确保 padding 不改变 max 和 exp-sum。此实现避免多 kernel 中间写回，但若 $N$ 很大，一行无法高效驻留寄存器，需要多阶段/online softmax 或专门库。

## 8. Row Sum：理解归约

对矩阵 $X\in\mathbb R^{M\times N}$：

$$
y_i=\sum_{j=1}^{N}X_{ij}.
$$

一个 program 处理一行时，load 是连续的，归约由 Triton 在 warp/block 内生成。关键参数：

- `BLOCK_SIZE >= N` 且通常取 2 的幂；
- padding `other=0`；
- 累加 dtype，低精度长归约应使用 FP32；
- 行 stride，输入非连续时不能假设等于 $N$。

若每行很短，单 program 工作不足；若很长，register 压力过大。可改为多个 programs 计算 partial sums，再第二阶段归约，但这会多一次 global memory 往返。

## 9. Fused Matmul + ReLU

目标：

$$
C=\operatorname{ReLU}(AB).
$$

若先调用 matmul 再 ReLU，$C$ 会写 HBM 后重新读。融合把 ReLU 放到 GEMM epilogue，只写最终结果。

### 9.1 二维 tiling

每个 program 负责 $C$ 的 `BLOCK_M × BLOCK_N` tile：

1. 由 `pid_m,pid_n` 得到输出行列 offsets；
2. 沿 $K$ 维按 `BLOCK_K` 循环；
3. load $A_{tile}$ 和 $B_{tile}$；
4. `acc += tl.dot(a,b)`，通常 FP32 累加；
5. 循环结束后 `acc = max(acc,0)`；
6. cast 到输出 dtype 并 masked store。

数学工作量：

$$
2MNK\ \text{FLOPs}.
$$

tile 让 A/B 数据在片上被多个输出复用，`tl.dot` 映射到 Tensor Core。输出 epilogue 融合几乎不增加 HBM bytes。

### 9.2 Program ID 排列

简单 row-major 地遍历输出 tiles 不一定有最好 L2 reuse。常把多个 M tiles 分组，在组内遍历 N，使相邻 programs 重用 A 或 B 的 cache lines。Triton 教程中的 grouped ordering 正是在控制 tile 调度的空间局部性。

### 9.3 参数选择

`BLOCK_M/N/K`、`num_warps`、`num_stages` 共同影响：

- Tensor Core 对齐；
- shared/register 占用；
- pipeline load-compute overlap；
- 边缘浪费；
- occupancy。

最佳配置依赖 shape 和 GPU，通常需 autotune，但 autotune 搜索也必须在真实 shape 分布上进行。

## 10. 从 Triton 到 PTX

检查生成 PTX/汇编可回答：

- 是否出现预期 tensor-core MMA 指令；
- load/store 宽度与地址计算是否合理；
- 是否因 register 不足发生 local-memory spill；
- 分支和 mask 是否过多；
- 编译器是否完成 fusion/constant folding。

但汇编是诊断证据，不应脱离 profiler 指标和端到端 benchmark 单独优化。

## 11. Kernel 验收矩阵

### 功能维度

- 整除/非整除；
- 小于一个 block、恰好一个 block、多个 blocks；
- FP32/BF16/FP16；
- contiguous 与显式拒绝/支持非连续；
- 极值、NaN、空 tensor；
- forward 和需要时的 backward。

### 性能维度

- 小、中、大代表性 shapes；
- 与 eager、builtin、compiled baseline 同条件；
- latency、GB/s 或 TFLOP/s；
- profiler 中 kernel 数、HBM、occupancy；
- 多次重复 median，不只报告单一最快值。

## 12. 常见误区

- `torch.cuda` 调用是异步的，CPU wall-clock 直接计时会错误。
- 编译后第一次运行包含 JIT，不代表稳态性能。
- 一个更少 FLOPs 的公式可能产生更多 HBM 访问。
- Triton 自动生成线程映射，但不会替你选择正确数据布局和 tile。
- softmax padding 用 0 会改变最大值/分母；max 归约应填 $-\infty$。
- 只测整除 shape 会隐藏越界和性能断崖。
- 自定义 kernel 快于 naive Python 不代表快于厂商库或编译器。

本讲的完整工作流是：写清数学语义，建立 reference，设计数据块和 HBM 流量，编写 masked kernel，做跨 shape 正确性测试，再用 benchmark、profiler 和必要的 PTX 检查证明收益。
