## 一、这一讲在课程里的位置

L02 讲了"推理时多想"（test-time scaling），L04 讲了"从执行反馈中学习"。软件工程是这两条主线**最自然的交汇点**：代码天然可执行、可验证（测试通过/性能数字），天然支持多轮编辑-运行循环。这一讲回答的问题是：**把前两讲的方法论放到真实、肮脏、长上下文的软件工程任务上，还成立吗？**

答案分两半：在 SWE-bench（修 GitHub issue）上，方法论成立且成绩亮眼（CodeMonkeys）；在 GPU kernel 优化这种"正确只是起点、性能才是目标"的任务上，方法论部分成立但暴露了基础模型的硬瓶颈（KernelBench）。

## 二、核心概念

- **SWE-bench / SWE-bench Verified**：从真实 GitHub issue 构建的软件工程基准，任务是修改代码库让隐藏测试通过；Verified 是经人工筛选的 500 题高质量子集。
- **串行 vs 并行测试时计算（serial vs parallel test-time compute）**：串行 = 单条轨迹上迭代更多轮（编辑→运行→再编辑）；并行 = 同一问题采样多条独立轨迹。CodeMonkeys 的核心设计就是同时扩展这两个轴。
- **成本摊销（amortization）**：并行采样多条轨迹时，前期成本（如理解代码库）可以在多条轨迹间摊销——这是"让 LLM 读遍每个文件"这种奢侈做法变得划算的原因。
- **候选选择（candidate selection）**：并行采样 N 个候选补丁后，如何挑出最好的一个。CodeMonkeys 的方案 = 模型生成测试投票 + 专门的选择轨迹。
- **fast_p 指标**：KernelBench 提出的指标——生成的 kernel 既**功能正确**、又比 PyTorch 基线**快超过阈值 p** 的任务比例。fast_0 即纯正确率，fast_1 即"正确且更快"的比例。
- **迭代细化（iterative refinement）**：每轮把上轮生成、执行结果、profiler 输出反馈给模型再生成——L04 执行反馈思想在性能优化任务上的直接应用。

## 三、论文精要

### 3.1 《CodeMonkeys》

- **一句话贡献**：把"串行迭代 × 并行采样 + 测试驱动选择"的测试时计算扩展方法论系统性地搬到 SWE-bench，用约 **2300 美元**预算在 SWE-bench Verified 上解决 **57.4%** 的 issue；其选择方法还能融合不同来源的候选补丁，把多个顶尖提交组成的集成选到 **66.2%**，超过集成中任何单个成员。
- **方法（三个关键设计）**：
  1. **联合生成编辑与测试**：模型每轮在产出草稿补丁的同时，生成并运行一个测试脚本来自检——把验证器（L03）直接织进生成循环。
  2. **两轴扩展**：串行方向增加每条轨迹的迭代轮数；并行方向增加轨迹数。并行扩展带来一个副产品——**前期成本摊销**，于是可以用最笨但最可靠的方式找上下文：让 LLM 把代码库每个文件都读一遍。
  3. **两阶段选择**：先用"模型生成的测试"对候选补丁投票，再用一条专门的多轮选择轨迹做终选。该选择器与生成器解耦，因此能用来挑**别家系统**产生的补丁（集成分来源候选 → 66.2%）。
- **与课程主线的关系**：这是 L02「重复采样 + 验证筛选」与 L04「执行反馈」在工业级任务上的完全体，也再次印证课程反复强调的一点——**选答机制（selection）和生成能力同等重要**。
- **局限**：预算随串行轮数与并行轨迹数线性增长；选择器仍是 LLM，面对 N 个都似是而非的补丁时没有银弹。

### 3.2 《KernelBench》

- **一句话贡献**：提出 250 个真实 PyTorch 工作负载组成的 GPU kernel 生成基准与 fast_p 指标，系统测出当前 LLM 的硬边界——**最强推理模型 one-shot 也只有不到 20% 的任务能同时做到"正确 + 比 PyTorch 快"**。
- **基准结构**：Level 1（100 题，单算子：卷积/矩阵乘/激活/LayerNorm）→ Level 2（100 题，3–6 个算子的序列，可融合）→ Level 3（50 题，完整网络如 AlexNet、MiniGPT）。正确性用 5 组随机输入校验，性能预热 3 次后测 100 次取均值。
- **关键结果**（vs PyTorch Eager 的 fast_1）：
  - one-shot：DeepSeek-R1 在 L1/L2/L3 分别为 **12% / 36% / 2%**；OpenAI o1 为 10% / 24% / 12%；GPT-4o 仅 4% / 5% / 0%；Llama 3.1-405B 全面扑街（3% / 0% / 2%）——**堆参数不解决 kernel 问题**
  - **重复采样有效**：DeepSeek-V3 在 L2 上 k=100 时 fast_1 从 4% → **37%**（典型的 L02 幂律现象）
  - **迭代细化更强**：给 DeepSeek-R1 反馈"上轮生成 + 执行结果 + profiler 输出"跑 10 轮，L1/L2/L3 从 12% / 36% / 2% → **43% / 72% / 18%**；同等预算下，迭代细化在 6 个对比中的 5 个优于纯重复采样
- **最刺眼的发现**：
  - 推理模型（o1/R1）错误率 <55%、其他模型 >70%，但差距几乎全部来自**执行错误更少**——"**所有模型在功能正确性上挣扎的程度差不多**"
  - 能力天花板真实存在：DeepSeek-V3 对 L1 里 34 个卷积变体，**采 100 次也做不出一个正确的**
  - 模型学会了算子融合（GELU 2.9×）、shared memory 利用（2.8×）、算法级优化（稠密×对角矩阵 13×），但**从未成功使用 tensor core 指令**——而这是现代 GPU 性能的关键
  - 根因之一：CUDA 在 The Stack 语料中只占 **0.073%**，是典型低资源语言
- **与课程主线的关系**：KernelBench 是课程结论的最佳注脚——测试时扩展能把"取出来"的能力稳定化（正确率、可运行率大幅提升），但**不能凭空创造训练时没有的能力**（tensor core、深度性能优化直觉）。
- **局限**：fast_p 阈值越高达标率越低；跨硬件泛化差（R1 在 L40S 上 L2 fast_1=36%，换 A10G 变 47%）。

## 四、放进课程主线里看

两篇论文构成一个对照实验：

| | CodeMonkeys（SWE-bench） | KernelBench（GPU kernel） |
|---|---|---|
| 任务性质 | 修 bug：正确即可 | 写 kernel：正确 + 要快 |
| 验证器 | 测试通过/失败（强、便宜） | 正确性 + wall-clock（强，但性能目标没有上限） |
| 测试时扩展效果 | 好：57.4%，且选择器可复用 | 部分有效：正确率大升，性能达标仍 <20% |
| 瓶颈 | 成本、选择精度 | **基础模型的功能正确性与性能直觉** |

结论和整门课完全一致：**可验证性决定方法论是否成立，基础能力决定天花板在哪**。SWE-bench 上"修对"是可判定的，闭环就转得动；kernel 优化上"快"没有饱和点、正确性本身又超出预训练覆盖，闭环就卡在半途。

## 五、如果自己动手

1. **给你的 agent 写测试，而不是只靠评审**。CodeMonkeys 的关键一步是让模型边改边生成测试脚本并运行——生成器自带验证器，选择阶段的压力骤减。
2. **两轴预算分开调**：先加串行轮数（便宜、收益直接），再加并行轨迹（可摊销前期成本）；别一上来就 N=100 平行采样。
3. **选择器单独做**：一个专门的多轮"选答"轨迹 + 测试投票，比让生成器自评靠谱得多——而且这个选择器可以拿去挑别的系统的产出。
4. **迭代细化优先于重复采样**：有执行反馈可用时，同样预算下细化 10 轮通常优于采 10 个独立样本（KernelBench 6 个对比赢了 5 个）。
5. **先查语料覆盖再定预期**：任务所用语言/领域在预训练语料里占比多少（CUDA 只有 0.073%），直接决定你该期待"闭环改进"还是"先补基础能力"。
