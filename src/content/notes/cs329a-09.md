## 一、本讲要解决什么问题（TL;DR）

作为本门课的最后一讲，两位讲师做了两件事：前半场由 Aakanksha 用三篇最新论文（多智能体微调、DeepSeek-Math V2 的自我验证、模型自出题的 Absolute Zero）串起"自我改进"这条主线，回答**当前的自改进循环到底卡在哪三处**——推理链的多样性不足、验证器（verifier）不可靠、训练数据与题目依赖人类专家；后半场由 Azalia 切换到"智能的成本"视角，用她与 Hennessy 等人合作的 **intelligence per watt（每瓦特智能）** 研究说明：绝大多数真实请求其实不需要前沿大模型，本地模型 + 本地硬件正在快速追上，未来的关键资源是能源而非参数量。两人最后把两半场合成一张"未解决地图"：测试时扩展的基础原理、持续学习（continual learning）、高吞吐低延迟推理基础设施、混合云—端 serving、面向能耗的新架构与 kernel。结尾两位讲师致谢，并说明评分与课程项目以 poster 形式收尾。

## 二、核心概念与术语

- **自改进循环（self-improvement loop）** → 模型生成解 → 验证器给反馈/奖励 → 用 RL 或搜索让模型"爬山"→ 再生成的闭环。为什么重要：它是全课的组织骨架，本讲全部讨论都围绕"这个闭环哪里会断"。
- **Agent（智能体）** → 对 LLM 的推广：有目标、能和环境交互、收集反馈并据此纠正自己的步骤，能调用工具最终达成目标。为什么重要：课程叫 self-improving *agents* 而不是 self-improving *LLMs*，区别在于"自我导向 + 纠正"而不只是"输出文本"。
- **测试时扩展（test-time scaling）** → 推理时多次采样、多数投票（majority voting）、搜索、自我辩论来提升表现。为什么重要：当前提升性能最直接的手段，但代价是推理成本暴涨（本讲后半场的出发点）。
- **训练时扩展（train-time scaling）** → 把推理回路中得到的反馈变成奖励，用 RL 回灌到权重。为什么重要：与测试时扩展共同构成"自改进"的完整回路。
- **拒绝采样微调（rejection sampling fine-tuning, RFT）/ STaR** → 模型自己生成解、过滤掉错的、只在正确的上做 SFT，可加入推理链。为什么重要：这是最朴素的合成数据自改进范式，也是本讲三篇论文要超越的基线。
- **多样性坍塌（diversity collapse）** → 单一 LLM 反复生成数据时，即使高温采样，输出也高度同质，导致几轮到几十轮迭代后性能停止增长。为什么重要：这是自改进的第一道天花板。
- **结果奖励模型（outcome reward model, ORM）** → 只看最终答案是否匹配 ground truth 给奖励。为什么重要：简单可靠，但"答案对、推理错"时无法纠正，且在定理证明等需要严格推导的领域不适用。
- **元验证（meta-verification）** → 再叠一层模型去审查"验证器指出的问题是否真的存在、打分是否与问题相称"。为什么重要：它把"LLM as a judge 会幻觉出错误"这一漏洞堵上，是 DeepSeek-Math V2 的核心新增模块。
- **自出题 / 自提出任务（self-proposed tasks）** → 模型既当出题者（proposer）又当解题者（solver），在无人类数据的前提下自我生成课程。为什么重要：打破"必须有人类专家出题"的数据壁垒。
- **溯因 / 演绎 / 归纳（abduction / deduction / induction）** → Absolute Zero 构造的三类编程任务：演绎=给程序生成输入再执行得输出；溯因=反推；归纳=采样已有程序、生成新输入加自然语言功能描述再执行。为什么重要：它们定义了"无人类数据时任务从哪来"的具体机制。
- **课程学习 / 任务缓冲区（curriculum learning / task buffer）** → 把 (输入, 输出, 程序) 三元组和成功率存入缓冲区，出题者从中采样参考并按难度演化。为什么重要：让任务难度随模型能力自动上移。
- **Intelligence per Watt（IPW，每瓦特智能）** → Azalia 团队提出的新指标：平均任务准确率 ÷ 平均功耗。为什么重要：它同时刻画能力与效率，是判断"能不能搬到端侧跑"的统一标尺。
- **本地模型（local model）** → 本研究的界定：活跃参数量 ≤ 20B 的模型。为什么重要：这是"能不能塞进笔记本/手机"的量化门槛。
- **合成数据飞轮（synthetic data flywheel）** → 模型生成数据 → 训练后更强 → 生成更好数据的正反馈。为什么重要：讲师认为它是当前最大的新现象，也是通往持续学习的入口。
- **持续学习（continual learning）** → 模型像人一样在做事的过程中持续把正负经验吸收进能力，而不是"离线攒数据 → 异步微调"。为什么重要：当前范式与人类学习方式之间存在明显错配，是两人共同点名的最大空白。
- **不可验证领域（non-verifiable domains）** → 奖励信号极慢或主观的领域（芯片设计跑几天仿真、湿实验、创意写作）。为什么重要：绝大多数自改进方法在此失效，是泛化的主要边界。

## 三、主线内容

### 3.1 开场：回看整个学期的版图（[00:05]–[04:10]）

Aakanksha 的回顾顺序是：课程从 LLM 概览起步，核心是**测试时扩展**与**训练时扩展**，基本回路由验证器（verifier）+ 奖励 + RL + 搜索驱动，在数学和代码上爬山；接着讲**演化策略与开放性（open-endedness）**，即不只靠奖励，还允许模型在可定义空间里自由探索（AlphaEvolve 一类）；然后转向**端到端 agent 工作流**——工具调用、检索、记忆、多步规划与推理，以及"下一代模型该怎么评测"；期间穿插了 post-training、多模态 agent、机器人、推理等客座讲座。Azalia 补充：某位客座讲者讲的**符号技术（symbolic techniques）**也归入工具使用，可用于合成数据，这是当下另一条趋势。

随后 Aakanksha 重申第一讲的定义：**agent 是 LLM 的推广**——有目标、与环境交互、收集反馈、用反馈纠正步骤，即"能指挥自己的流程、使用工具、达成目标的系统"。她给出当前范式的判断：LLM 本身往往还不足以独立驱动完整目标，所以今天大量系统仍是**人手写的 workflow**（编排 LLM + 工具）；但在 coding agent 等场景已经看到 workflow 开始由模型自己驱动。构造这类 workflow 意味着要同时编排 LLM、验证器（可能需要 LLM as judge）、工具调用和搜索算法（并行 LLM 调用做搜索），而 agent workflow 要朝目标前进，就**必须有多步规划与推理、走错时自我纠正、并持续提升能力**——自改进由此进入。

### 3.2 本讲的组织逻辑（[04:10]–[06:12]）

两位讲师把最后一讲分成两半：Aakanksha 讲三篇论文的**关键思想**（不是逐行讲算法，而是说清"为什么选它、它指向什么下一步"），覆盖自改进侧；Azalia 讲**智能的效率（efficiency for intelligence）**。Aakanksha 明确点出三个待解问题：（1）测试时/训练时扩展目前仍局限在数学与代码等窄域，如何跨域泛化、如何让推理链足够多样以维持回路；（2）**验证仍是构建自改进回路的关键**，需要鲁棒的验证与元验证；（3）即使谈训练时扩展，**喂进训练的 prompt 仍是静态挑选、需要人来做**，如何打破数据壁垒。她还补了一句坦率的话：领域进展太快，"也许下次开课我们就会逐个讲这些论文了"。

### 3.3 论文一：Multi-Agent Fine-Tuning —— 用多样性打破天花板（[06:12]–[14:20]）

论文题目即 *Multi-agent fine-tuning: self-improvement with diverse reasoning chains*。出发点是：预训练算力是对互联网规模数据的压缩，指令微调则往往需要**真人偏好数据**来判断好回答与坏回答；替代方案是用 LLM 生成**合成数据（synthetic data）**做迭代微调——生成候选解、过滤掉错的（拒绝采样）、只在好的上微调，STaR 等变体是其增强版（课上已讲过 STaR）。

问题在于：**用单个 LLM 生成数据，解会高度相似，性能提升在几轮到几十轮迭代后就停止**，根因就是缺乏多样性。直觉解释：预训练数据之所以多样，是因为它由人类在漫长时间里产生；而单个 LLM 对一组 prompt 采样，**即使高温也不够多样**。

论文的对策是引入多个**专用化 agent**：训练 **generation agents（生成者）**产出多样的初始解，训练 **critic agents（批评者）**评估并refine。流程是：每个生成者先给出初始答案 → 把所有 agent 的回答做摘要（可用一个模型摘要，也可直接拼接）→ 批评者对这一"更新后的答案集"给出批评 → 批评被拼进输入，进入第二轮，各模型再生成更新答案 → 再次多数投票 + 摘要，如此形成**多轮辩论（debate）**。关键差异在于：批评不再针对单个 agent 的回答，而是**跨多个 agent 汇总后再批评**。这样做的好处是**在批评之前就已经有了多样性，多数投票几乎是白送的**——因为这些生成者从同一 base model 微调而来、但训练方式略有不同。每轮迭代后，用多数投票过滤出一致的 (prompt, response) 对做 SFT。讲师还给了个"穷人版"：直接用几个不同的模型 + 不同的 prompt，实践中很多人就是这么做的。批评者同样被微调，训练数据是"一开始答错、在辩论过程中被纠正"的混合轨迹，因此它学的是**对比正确与错误的答案**；这些辩论轨迹也可用于微调出不同的批评模型。

结果（在 math 数据集上）：左图 x 轴是微调迭代轮数，y 轴是**负对数似然（作为性能的代理指标）**或 **embedding 不相似度（值越高越多样）**。两个开源模型用多智能体微调能**持续提升性能**，其中 **Llama 3 对这种方法响应更明显**；右图更关键——随着迭代推进，**回答的多样性得以保持**。三个开源模型上重复实验（因为是做微调，只能用开源模型），多智能体设置下多轮微调仍在涨，而**单智能体微调的准确率会坍塌或停止提升**。此外，不仅在域内（math），在相邻域如 **GSM8K** 上微调后的 agent 也有更高性能——讲师坦承这是稍早的工作、绝对数字不高，但结论明确：**该方法能泛化到训练域之外**。

### 3.4 论文二：DeepSeek-Math V2 —— 自我验证与元验证（[14:20]–[22:27]）

第二个硬问题是验证。常见做法只看最终结果：数学题或定理证明对了就给奖励，即结果奖励模型（ORM）。课上验证那讲已讨论过：如果推理链是错的会怎样？会不会把模型带偏？而**过程奖励模型（process reward model）又很难建**。

DeepSeek-Math V2 试图证明：至少在定理证明领域，**自动化的自我验证回路是可行的**。当前 RL 范式假设"最终答案匹配 ground truth"就给奖励，这已经让 **AIME 等多个数学基准趋于饱和**（转写此处作 "AMIE"，疑为 AIME 之误，待核对），但**答案正确不等于推理正确**，而定理证明恰恰要求严格的逐步推导。更棘手的是：LLM 常受定量推理训练，生成的证明**可能数学上无效**；让它去验证，它会把无效证明判为有效——**LLM as a judge 在这里不好使**。而专家人类能看出"这一步推不出上一步""证明里有推理缺口"。

DeepSeek-Math V2 的做法：不是只训练奖励模型，而是训练**验证器（verifier）**，即让人类**在没有任何参考解的情况下**指出证明中的问题，据此训练 LLM 去识别问题并改进；再引入**元验证器（meta-verifier）**这一新模块——它审查"验证器的分析是否讲得通、指出的问题是否真的存在"。验证器被训练成按 **0.5 与 1** 的分数量化证明质量。于是形成回路：**验证器改进生成器 → 生成器产出更难的证明 → 反过来实现验证器**。另一个要点是**标注可自动化**：一旦用人类标注作为种子教会模型找错，后续就能自动打标，不必一直依赖人类。

元验证的意义很具体：**当推理链本身有误时，验证器仍可能给出"正确"的分数——例如它编造（fabricate）了一些错误**。元验证就是问：验证器（此处的 LLM as a judge）指出的这些问题**真的存在吗？分数与问题相称吗？**专家再对这层评估的质量做人工标注。仅靠加这一个模块，质量就提升了。讲师的类比很精炼：原来有推理链，现在有了**推理链之上的验证器**，再往上还有一层判断"这个评估对不对"。

结果：基于 **DeepSeek V3 base**、在 GRPO 之上做迭代优化，基准是 **IMO 题目与 CNML 题目**（IMO 部分此前由一位客座讲者讲过 Gemini 版本，这是最近放出的**开源版本**）。**8 轮迭代**内，仅用 positive@1，证明分数就持续攀升；若用 **best@32**（从 32 个生成的证明里挑最好的），在 **IMO Shortlist 2024** 上证明分数几乎达到 **42%**。讲师评价这是一个很有希望的爬山技术，说明"**能定位推理链中的问题并推动模型去纠正**"是有效的：最好的证明拿到更高的验证分，生成器学会区分高质量证明与有缺陷的证明，自我验证因而改善了整个回路。**验证可以是瓶颈，这是打破瓶颈的一条路。**

推广到其他领域的三条要素：① 基于 LLM 的验证器要能**在没有参考解的情况下**找出问题（这篇论文正是依赖这点）；② 需要一个**元验证模块**来降低验证器幻觉出问题的概率；③ 给生成器**额外的激励**，促使它通过审慎推理（deliberate reasoning）最大化质量。局限也讲明了：**这仍局限于验证较容易的领域**。

### 3.5 论文三：让模型自己出题（[22:27]–[31:40]）

第三问是"该在哪些数据/prompt 上训练"。当前 AI 训练栈中，监督学习阶段用**人工整理的推理轨迹（human-curated reasoning traces）**，RLVR 阶段则期望专家去整理问答对——做数学要数学专家、做 IMO 要 IMO 专家、做代码要强程序员。**随着模型逐渐超越人类智能，找专家、找题目的能力就开始成为限制。**

这篇论文的思路（据讲师说法，这是一个"还没被大量使用但很有前景"的新想法，课堂上未点名，但在 [64:30] 的学生提问中出现 "absolute zero paper"，且任务类型吻合，应为 *Absolute Zero: Reinforced Self-play Reasoning with Zero Data*，待核对）：**同一个模型既出题又解题**，走向另一个极端——**不需要外部数据源、不需要人类生成的 prompt**。它以**代码**为主要域，构造三类任务：**演绎（deduction）**——生成程序与输入、环境执行得到输出；**溯因（abduction）**——同样生成程序与输入、环境执行，但方向相反；**归纳（induction）**——采样一个已有程序，为其生成新输入 + 一段描述其功能的自然语言信息，再由环境执行判定。出题者还会**以过去生成的样例为条件**（显式拼进 prompt）以促进多样性。整个过程分两阶段：**提议阶段**按任务类型构造任务并用奖励筛选；**求解阶段**做验证并给出准确率奖励；两者共同对模型做**联合更新**，而不是单边更新。

**出题者的奖励怎么定？** 每个生成的任务交给 solver，若**成功率为 0 则奖励为 0**；若成功率非 0，奖励为 **1 − 平均成功率**。也就是说要挑**既非平凡也非不可能**的任务——solver 有时成功有时失败，学习信号最强。出题者的目标是在当前权重下生成**最优难度**的任务，而随着模型变强，出题者应学会出更难的题。为保证任务有效，代码抽象允许做**程序完整性检查（program integrity）**：能真正执行、能做安全检查、能多次运行确认输出一致（这在代码里可行），从而在进入训练管线前**验证被提议的任务**，防止出题者 hack 出一堆垃圾任务。同时维护一个**任务缓冲区（task buffer）**：每个 (输入, 输出, 程序) 三元组及其成功/失败次数都存进去，出题者可从缓冲区采样参考——这就形成了一条**随时间演化的课程学习**曲线。

效果：在**代码基准上达到 SOTA，尽管 prompt 侧完全没有人工整理的数据**，并且**超过了用数万条专家样例训练出来的模型**。涌现行为包括：复杂度指标随时间上升（出题者持续加难度）；在回路搭建正确时，程序与答案的多样性在改善；出题者在训练推进中确实持续生成更难的题。讲师的比喻是：**出题者与解题者略带对抗性，但总体互相成就**，有点像博弈论。更令人意外的是：即使只在自提出的代码任务上爬山，模型在**代码和数学基准上都有很强的表现**——这点反直觉，但可以用领域内其他结果解释。另外，**更大的模型相对小模型获得更大的收益**。

### 3.6 讨论：合成数据飞轮与"不可验证"的边界（[31:40]–[39:58]）

Azalia 在这里做了一次重要的纵向串联：她认为 Absolute Zero 的发现与课上讲过的 **SWiRL（step-wise / step-by-step RL with synthetic data，转写记作 Swirl）互相印证**——存在一条被反复观察到的趋势：**模型自己生成合成数据，不只提升生成时所针对的任务，还带来可迁移性**。SWiRL 原本做的是带检索的多跳问答，但随着合成数据增多、RL 训练推进，模型在**其他工具调用**上也变好了，比如调 Python 解数学题，反之亦然。第二个共振的观察是：**更大的模型更擅长吸收这种数据飞轮并从中泛化**，至少 SWiRL 在 RL 优化侧是这样。

Aakanksha 的三点小结：① 要达到真正的泛化与推理，**推理链必须有多样性**，而如何实现多样性仍是开放问题；② 需要更好的验证，**越能摆脱"只能由人类专家验证"的束缚越好**，建奖励模型本身很难；③ **数据（prompt）的选择**本身也是壁垒。

Azalia 补了一个她认为最有意思的方向：在可验证域里把自改进推到极致，看**性能能提升多少、又能泛化到多少没有自动验证的域**——能不能让模型在可验证的地方不断变聪明，从而**减少甚至消除不可验证域对标注数据的需求**。她同时提醒这是**计算密集型的实验**。

关于"哪些 AI 应用不属于可验证问题"，两位给出了清晰界定：Azalia 说的是**验证极慢**的领域——**科学发现**、**芯片设计里跑一次要几天的仿真**、**必须进湿实验室做化学实验才能拿到奖励**的场景。她的判据很实用：RL 微调或测试时扩展都要求验证器**近乎即时**，也许能等几分钟、最多一小时，但 RL 训练要成百上千步迭代，**不可能等上几天，也不可能有 human-in-the-loop 收奖励**。Aakanksha 补充还有**真正不可验证**的一类：**创意类 / 主观性指标**（如创意写作）——为它设计精确的奖励函数很难；当然总能建模，但**只要模型略有偏差，RL 或 agent 就会去 reward hacking**。

学生追问"人们怎么尝试解决芯片设计、生物发现这类难题"，回答是两条路径：Azalia 说**训练一个独立的奖励模型去预测仿真结果**——离线收集大量数据，训练一个"给定输入预测输出质量"的奖励模型，把它当作 RL 回路里的验证对象；但**奖励模型的泛化能力取决于你有多少数据，而且可能不准，这会带来问题**。Aakanksha 给的是**问题分解**路径：以斯坦福的 **KernelBench**（她称"你们实验室的工作"）为例——生成的代码能否通过编译、能否执行，这些是能拿到指标的；但有个课程项目试图**阅读性能剖析（performance profile）并在复杂化后优化代码**，这就是更难的问题。即便模型能优化单个 kernel，把多个 kernel 拼起来后做性能剖析、改动未优化的部分仍然困难。因此现实做法是：**把问题拆成模型当前能力能解决的子部分，配合参考解和知识库**——她直言"我刚才其实就是在描述一个课程项目"。要点是：**因为问题足够难、模型能力还不够，往往需要以有趣的方式分解问题来适配模型当下能做的事**。

### 3.7 Azalia：Intelligence per Watt 与本地推理的兴起（[39:58]–[51:12]）

转入效率议题。Azalia 介绍的是她与 **Professor Ray、Professor John Hennessy** 及一个大团队的近期合作工作：同时观察**模型侧**与**硬件加速器侧**的趋势，思考未来 AI 推理的负载形态——需要多大规模的模型、需要什么样的加速器来服务它们。

**现状判断：我们处在"大型机（mainframe）时代"。** 我们用的 ChatGPT、Gemini 等大模型全部跑在云上：模型太大跑不动本地、有些是闭源拿不到权重、即便是开源的大模型也仍然在用云端跑。同时**算力需求在爆炸**：转述 Google Cloud 在过去约 12–20 个月内算力服务增长了约 **1200 倍**（转写原文 "in the last 12 20 months" 数字表述含混，待核对），Nvidia 有约 **10 倍的年同比增长**；结果是当下需要约 **250 吉瓦（gigawatt）级的数据中心**来满足需求，而且还在涨，意味着需要越来越多的能源供给。右侧的 Google token 处理量曲线同样惊人：**去年 2 月是 160 万亿（trillion）token，今年 10 月是 1.3 千万亿（quadrillion）**——"历史上增长最快的算力需求之一"。

**但需求结构并不匹配这个供给方式。** 来自大规模 ChatGPT 用户数据集的统计显示：约 **77% 的请求**属于**实用指导、信息查询、写作**这类任务，而**这些任务并不需要最好的前沿模型才能答对**，更小、可本地运行的模型就够了。右侧的查询类别随时间变化图还显示：虽然用户会随聊天机器人变强而问更复杂的问题，但**绝大多数查询仍处在较简单的复杂度一侧**，可由小模型而非大型闭源模型处理。

**第三条趋势是本地推理加速器的进步。** 右侧图显示：**自 2012 年至今，本地加速器的 GPU 显存提升了约 126 倍**；现在我们的 MacBook 可以有约 **100GB 内存**，这意味着**如果以量化版本（例如 8-bit）服务，连一些最大的模型都能塞进本地跑**。这条趋势与"大量查询可被小模型解决"相互呼应。

于是研究问题是：**本地推理能在多大程度上重新分配推理需求？** 目前几乎所有流量都涌向云端的 H100、TPU、GB200/GB300（转写作 GP200/GP300，待核对）等加速器，但趋势暗示可以换个做法。

为了系统研究，他们定义了一个新指标 **intelligence per watt（IPW，每瓦特智能）**，同时刻画能力与效率：能力侧看**模型可处理的单轮与推理型查询的百分比**（本研究中"本地模型"界定为**活跃参数量 ≤ 20B**）；效率侧看在本地硬件上运行这些模型时每瓦特能拿到多少有效算力。简言之：**IPW = 平均任务准确率 ÷ 完成任务所需的平均功耗（power draw）**。

实验覆盖面：模型侧看了 **20 多个本地模型**（quant、GPTQ、Llama 3 等）；硬件侧同时看**企业级加速器与本地加速器**；负载侧用了**来自 ChatGPT 的 100 万条查询**，外加 **Natural Reasoning、MMLU Pro、Super GPQA** 等推理基准；评测指标包括准确率、能耗、延迟、所用算力等。这批大规模数据既用于分析趋势，也已**开源**了不同模型与硬件底座上的各类指标。

**三项核心发现：**
1. **本地模型不仅已经很强，改进速度更值得注意**——自 2023 年以来，其准确率（即可解决的聊天查询占比）提升了 **3.1 倍**，只用了 **2 年**；目前在上述查询集上能处理约 **88.7%** 的请求。
2. **本地加速器在效率上落后于企业级芯片**——例如 **Apple M4 Max 的每瓦特智能比 B200 低 1.5 倍**。原因是 B200 这类芯片被极致优化来跑语言模型负载，而 Apple M4 虽然也为 AI 指标做了优化，但还要兼顾其他负载；更根本地，**芯片设计者在设计时并没有预期 LLM 会跑在本地**，所以绝大部分精力放在了云规模芯片上。
3. **IPW 在过去两年提升了约 5.3 倍**，其中 **3.1 倍来自模型进步**，**1.7 倍来自硬件效率提升**。

结论指向一个未来：**越来越多流量可以由端侧设备（笔记本，未来是手机）上跑的模型来处理**。

### 3.8 效率视角下的开放方向（[51:12]–[58:20]）

Azalia 列出三组方向。**第一组（自改进与学习范式）：**
- **测试时扩展的基础原理（foundational principles in test-time scaling）**：当前做法是 RL + 收集数据 + 微调，但"这里面还有更多东西"。核心开放问题是：反复就同一问题多次采样时，**模型内部到底发生了什么，才让正确答案浮现出来**？以及**把成功轨迹蒸馏回模型的最佳实践是什么**？
- **从合成数据飞轮到持续学习（continual learning）**：这里存在明显错配——人类在解决问题、学习新事物的过程中能力持续发展；而模型主要是**离线的**：某个 agent 攒一批经验，过一段时间再做一次微调，**不是边做边学**。持续学习要回答的是：有没有不同于"异步生成数据 + 微调"的新范式，能把正面经验、从失败中学到的东西、模型的问题求解过程更自然地灌回模型。
- **高吞吐、低延迟的测试时扩展基础设施**：测试时扩展（重复采样、对前序生成做反复修正、工具调用等）与当前主流聊天机器人"单轮来回"的形态**非常不同**，这意味着**大量的系统与推理优化机会**。Azalia 的实验室做过 **Hydragen（转写作 hydrogen，待核对）**、**Tokamak**（待核对）这类工作，"随着这些方法走向主流，它们会越来越重要"，需要有针对性地优化系统与底层算力。

她用一张图收束整个学期：**预训练**这块本系列讲座涉及较少（尽管 Aakanksha 是预训练专家），课程**主要聚焦 post-training 与测试时扩展**；而在**微调、在线学习、测试时扩展之间的连接处**，出现了一片"被释放出来的新领域"——**合成数据飞轮与持续学习**——希望大家既学到了很多，也看到这里有大量尚未解决的挑战可以去做。

**第二组（本地化带来的新方向）：**
- **混合推理服务引擎（hybrid inference serving engines）**：能在本地与云端的模型和加速器之间，依据需求与资源复杂度**平滑地路由流量**。
- **面向高能效推理的新模型架构与 kernel**，尤其是面向**本地加速器**的——相比云加速器，这块受到的关注少得多。
- **能源将成为未来最有价值的资源**：像 intelligence per watt 这样的指标、更好地理解与度量能耗/功率并据此优化，会变得非常重要。目前**以能耗作为目标优化指标还少有人关注**，但预计会走向主流。

### 3.9 Q&A 与结课（[58:20]–[66:43]）

**Q1（关于持续学习落在记忆系统还是模型本身）**：Aakanksha 回答：持续学习若类比人类，确实与长期记忆系统相关，但**在走到那一步之前**，更基本的问题是：在多步推理中从成败中学习、把技能保持并更新到**权重（或权重的子集）**里——"模型能不能学会一项新技能？能不能学会学习？"这是目前**基本不具备的能力**。举例：机器人能不能**只看视频就学会做一件事**，而不必被喂大量任务示范？Azalia 补充了**不改权重的另一条路**：如果模型有**近乎无限的上下文**并且能完美访问其中每一部分，那本身就是持续学习的一种解法——把所有正负经验都放进上下文，模型同时记住并推理；可惜我们没有，即便到百万级上下文，**模型在 ICL 内容上的推理能力也会衰减**。其他路径还有课上讲过的 **Cartridge**（转写作 cartridge，待核对）——**不改权重、不微调**，而是把知识带进激活/ **KV cache** 中以实现长上下文与 in-context learning。所以持续学习可以不靠微调，而是靠**大幅提升有效上下文长度**。

**Q2（实践中更新权重 vs 更新记忆库哪个更容易）**：Aakanksha 的回答是"取决于应用"。最简单的版本：如果 LM 能学会去查一个数据库，那就去更新数据库（知识库）。但**你真正想教给 LM 的是在新领域上推理的能力，而外挂一个旁路记忆系统往往做不到这一点**——这正是更新权重更胜任的地方。她的机器人例子很贴切：周一那讲里看到的**跨本体泛化（cross-embodiment generalization）**，光靠记忆系统是不会发生的，必须更新 LM 权重——**这是技能迁移问题，不是知识检索问题**。

**Q3（关于 Absolute Zero 里"agent 自创环境"）**：Aakanksha 的回答把话题拉回本质：在"窄智能"时代，人们可以为游戏造仿真作为玩具任务的环境；**环境在当前世代之所以重要，是因为它们是真实世界任务的代理（proxy）**。所以问题不是"有没有一篇让 agent 自创环境的论文"，而是**你想表征的任务集合是什么**——如果容易仿真，那么用 agent 造还是用软件造都直截了当；真正的问题是**它是不是模型在真实世界中如何交互、如何拿到反馈的合理代理**。游戏的好处是**探索空间有限**，因此容易用代码和仿真来表征。

**结课**：Aakanksha 致谢——教这门课、为它制作内容是件愉快的事；这个领域演进极快，**现在教的任何东西到下一轮开课时都已成为历史**，但**你们学到的基础技术在很长时间里仍然极有价值，因为大量新东西仍建立在基础技术之上**。她表示很期待大家的**项目与 poster**。Azalia 致谢并坦言：备课过程本身也是她们的学习过程，很多主题非常新，她们自己也很兴奋，希望大家"陪伴我们走过这段旅程"，有所学、有所启发，并希望这只是大家在研究项目、工作与未来中做出更多成果的**开始**。

## 四、开放研究方向清单

1. **推理链的多样性生成** — 自改进回路需要足够多样的 reasoning chain，而"如何造出多样性"本身仍是开放问题；当前一条可行路径是多模型/多智能体生成 + 跨 agent 摘要与辩论（3.3 节的 Multi-Agent Fine-Tuning）。
2. **鲁棒验证与元验证（meta-verification）** — 越能摆脱"只能由人类专家验证"越好；需要让基于 LLM 的验证器**在无参考解的情况下**定位问题，并加一层元验证以降低"幻觉出的错误"（3.4 节）。
3. **过程级验证的自动化** — 过程奖励模型仍难建；把 DeepSeek-Math V2 这类自我验证回路从"验证容易的域"推广到更一般的域是明确缺口。
4. **打破数据/题目选择的人类壁垒** — 让模型自己提出训练任务（Absolute Zero 式 proposer–solver 自对弈），使自改进不再卡在专家出题（3.5 节）。
5. **面向最优难度的自动课程学习** — 用 1 − 平均成功率之类奖励挑"有时成功有时失败"的任务，配合任务缓冲区让难度随能力演化。
6. **合成数据飞轮的迁移性研究** — 反复出现的现象：自生成数据不只提升本任务，还迁移到工具调用等其他能力；其机理与边界值得系统研究（SWiRL 与 Absolute Zero 的共振）。
7. **可验证域 → 不可验证域的能力迁移** — 在可验证域做极致自改进，能否减少甚至消除不可验证域对标注数据的需求；讲师明确提醒这是**计算密集型**实验。
8. **慢验证领域的奖励建模** — 为芯片设计、湿实验、科学发现等训练"预测仿真结果"的替代奖励模型；其泛化性受数据量限制，且不准会带来问题。
9. **难验证问题的分解策略** — 当模型能力不足时，如何把复杂目标（如多 kernel 拼接后的性能剖析与优化）拆解为其当前可解的子问题，并配合参考解与知识库。
10. **主观/创意领域的奖励设计与 reward hacking 防护** — 创意写作一类无法精确定义奖励函数的任务，以及"模型化奖励 ⇒ agent 钻空子"的风险。
11. **测试时扩展的基础原理** — 反复采样为何能浮现正确答案？成功轨迹蒸馏回模型的最佳实践是什么？（Azalia 明确点名为开放问题）
12. **持续学习（continual learning）** — 从"离线攒数据 + 异步微调"转向更接近人类的边做边学；涉及技能获取、"学会学习"、从失败中学习。
13. **持续学习的非微调路径** — 大幅提升有效上下文长度，或把外部知识压缩进激活 / KV cache（如 Cartridge），从而不改权重实现长期记忆。
14. **权重更新 vs 外挂记忆库的适用边界** — 知识检索走记忆库足够，但**跨领域推理与技能迁移（如机器人跨本体泛化）需要更新权重**。
15. **高吞吐、低延迟的测试时扩展基础设施** — 与单轮聊天截然不同的负载形态带来大量系统/推理优化机会（Hydragen、Tokamak 一类工作）。
16. **新一代预训练研究** — 本季课程主要覆盖 post-training 与测试时扩展，预训练涉及较少，仍是重要方向。
17. **混合（local ↔ cloud）推理服务引擎** — 依据查询复杂度与资源状况平滑路由流量。
18. **面向端侧加速器的高能效架构与 kernel** — 相比云加速器，本地加速器的模型架构/kernel 优化关注严重不足。
19. **以能耗为核心的度量与优化** — intelligence per watt 一类指标、能耗测量方法与以能效为目标的优化，预计将从冷门走向主流。
20. **环境作为真实世界代理的有效性** — 关键不在"谁来造环境"，而在"这个环境/仿真是不是真实任务的合理代理"；游戏因探索空间有限而易于表征，真实世界则不然。

## 六、全课回顾

讲师在开场（[00:05]–[02:07]）给出的整门课脉络，按时间顺序是：

1. **LLM 概览** → 引入测试时扩展（多样本、多数投票）与训练时扩展（推理回路中的反馈 → 奖励 → RL / 搜索驱动模型在数学与代码上爬山），其核心回路由**验证器 + 反馈**驱动。
2. **演化策略与开放性（open-endedness）** → 不只靠奖励，还允许模型在可定义的探索空间里自由探索（AlphaEvolve 等）。
3. **端到端 agent 工作流** → 工具使用（tool use）与环境交互；多步任务需要**检索与记忆**；因此需要更好的**规划与多步推理**。
4. **评测** → 如何评价下一代模型、哪些能力会驱动下一代模型。
5. **客座讲座** → post-training、多模态 agent、机器人、推理，以及归入工具使用范畴的**符号技术**（可用于合成数据）。
6. **收束到 agent 的定义** → 有目标、与环境交互、收集反馈、纠正步骤、调用工具；当前仍需大量手写 workflow，但 coding agent 已开始自我驱动。

而在结尾（[55:16]–[56:17]），Azalia 用另一条轴重新切分了整门课：**预训练**涉及较少（尽管 Aakanksha 是预训练专家），课程主体是 **post-training 与测试时扩展**；而在**微调 ↔ 在线学习 ↔ 测试时扩展的连接处**，浮现出一片新领域——**合成数据飞轮与持续学习**，这也是她希望大家接下来去攻的方向。

一句话总结这门课的主线：**验证器驱动的反馈闭环（数学/代码）→ 开放探索 → 工具与环境的端到端 agent → 评测 → 而在"智能成本"这一侧，同样的闭环必须靠合成数据飞轮与更高的每瓦特智能来维持。**

## 七、动手启示

1. **先诊断你的自改进回路断在哪一环**：多样性、验证器、还是题目来源。三篇论文正好对应三种断点——如果迭代几轮后指标就不涨了，优先怀疑**多样性坍塌**（查 embedding 不相似度这类多样性指标，而不是只看准确率）。
2. **提高多样性未必需要复杂算法**：用不同的开源模型 + 不同 prompt 做并行生成，再对汇总结果做批评与多数投票，就是多智能体微调的"穷人版"，成本极低、可立即复现。
3. **给验证器加一层元验证**：如果你的 LLM-as-judge 会"编造错误"（声称某推理步骤有问题但其实没有），用"这个问题真的存在吗？打分与问题相称吗？"作为第二层判据，并用少量专家标注做种子，之后可转为自动标注。
4. **让题目难度自适应**：用 1 − 平均成功率（或等价的中等难度判据）筛题，剔除成功率为 0（不可能）与成功率过高（平凡）的任务，并把任务与其成败统计存进缓冲区形成演化课程；同时务必做**有效性校验**（代码域可执行 + 可安全检查 + 多次运行输出一致）。
5. **不可验证域的实用打法**：要么训练一个**替代奖励模型**去预测慢速仿真/实验的输出质量（注意其泛化受数据量限制）；要么**把难题拆成模型当前能解的子问题**（如 kernel 优化拆成单 kernel 优化 + 性能剖析 + 参考解知识库），这是课上被直接点名的课程项目思路。
6. **把"每瓦特"纳入你的评测指标**：报告结果时同时给准确率与能耗/延迟；判断一个任务是否值得上云，先问它是否落在那 77% 的"信息查询/写作/实用指导"区间、能否用 ≤20B 的量化模型在端侧解决。
7. **改权重 vs 加记忆，按问题类型选**：纯知识检索用外挂记忆库/数据库即可；涉及**新领域推理与技能迁移**（跨本体、跨任务）时，外挂记忆无效，必须走权重更新或长上下文方案。
